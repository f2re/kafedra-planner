# Разбор строк импортированного плана

## Зачем нужен отдельный слой

Реальный план кафедры — это не плоский список задач. Один DOCX/XLSX/PDF может содержать несколько таблиц, служебные строки, метаполя, произвольные колонки и составные мероприятия. Поэтому импорт не должен сразу превращать каждую видимую строку в окончательную задачу и затем заставлять оператора исправлять результат в отдельном окне.

Контур использует три уровня:

```text
неизменяемый document_version
        ↓
plan_source_rows        исходные строки/ячейки с локаторами
        ↓ 1:N
plan_items              подтверждённые рабочие задачи/рубежи
        ↓ 0:1
assignment              поручение; внутри него может быть несколько исполнителей
```

Это сохраняет прежний контракт `plan_item → assignment`: один пункт плана имеет не более одного поручения. Несколько задач из одной строки создаются как несколько обычных `plan_items`, а не как особое многозадачное поручение.

## Что сохраняется из документа

`plan_source_rows` хранит:

- устойчивый ключ строки внутри источника;
- таблицу/лист/страницу и номер строки;
- исходный текст строки;
- все доступные ячейки с номером колонки, подписью заголовка и локатором;
- детерминированное предложение полей задачи;
- ячейки, которым не найдено предметное поле;
- уверенность извлечения.

`plan_source_row_items` связывает исходную строку с созданными пунктами и фиксирует `split_index`. Связь одного `plan_item` с несколькими исходными строками запрещена, чтобы происхождение оставалось однозначным.

Исходный DOCX/PDF и `document_blocks` не изменяются. Для планов, импортированных до появления этого слоя, строки восстанавливаются лениво из сохранённых `document_blocks`; повторный разбор не требует повторной загрузки файла.

## Автоматическое предложение

Детерминированный разбор сначала ищет заголовок таблицы и сопоставляет реальные номера колонок, а не позиции непустых ячеек. Это важно для Word/Excel: пустая промежуточная ячейка не должна сдвигать дату в поле ответственного.

Из известных колонок предлагаются:

- номер пункта;
- название мероприятия;
- описание;
- дата/период;
- контрольный срок;
- ответственный;
- направление;
- ожидаемый результат;
- статус исходной строки.

Неизвестная колонка не выбрасывается. Её значение остаётся в `unmapped` вместе с подписью заголовка и может быть автоматически добавлено в комментарий задачи, например `Основание: Решение учёного совета № 7`.

LLM для этого не требуется.

## Пользовательский сценарий

После загрузки плана основной экран показывает не только итоговые пункты, но и блок «Разобрать строки плана».

1. Система сама обрабатывает документ и показывает количество строк, спорных строк и уже связанных задач.
2. По умолчанию первыми показываются строки, где есть неоднозначность, неизвестные колонки или отсутствует уверенное сопоставление.
3. При выборе строки справа открывается редактор на месте. Исходные ячейки доступны в раскрываемом блоке, предложенные поля уже заполнены.
4. Недостающую дату, ответственного, результат или комментарий можно дописать. Неизвестные ячейки по умолчанию сохраняются в комментарии и могут быть отключены явным выбором оператора.
5. Кнопка «Разделить на ещё одну задачу» создаёт дополнительную карточку задачи из той же строки. У каждой карточки собственные название, даты, направление, результат и режим исполнения.
6. Для `Поручения` можно выбрать несколько исполнителей и контролирующего. Для `Открытой задачи` исполнителей можно не назначать заранее.
7. Сохранение обновляет обычные `plan_items`, календарь, поиск и поручения. Повтор того же сохранения обновляет существующие связи и не создаёт дубли.

Техническая ошибка не очищает редактор. Уже созданное поручение не удаляется молча при попытке вернуть пункт в режим простой контрольной точки.

## API

```text
GET  /api/plans/:planId/source-rows
POST /api/plans/:planId/source-rows/:sourceRowId/materialize
```

`materialize` принимает массив `tasks`. Порядок массива задаёт стабильный `split_index`; повтор с тем же количеством элементов обновляет те же пункты. Если оператор прислал меньше задач, чем ранее было создано из строки, лишние существующие пункты сохраняются и возвращаются как `retainedItemIds`: система не уничтожает уже начатую работу неявно.

## Миграция и восстановление

Схема 26 добавляет только новые таблицы и индексы. Существующие `plans`, `plan_items`, `assignments`, документы и история не переписываются.

После обновления обязательны:

- `PRAGMA foreign_key_check` без ошибок;
- `PRAGMA quick_check = ok`;
- проверка перехода существующей schema 25 → 26;
- резервное копирование всей SQLite-базы и blob-хранилища;
- восстановление без потери исходных документов и связей строки с задачами.

SQLite-backup копирует новые таблицы вместе с основной базой. В release evidence эти таблицы должны рассматриваться как устойчивые предметные данные.

## Регрессия

Unit/integration проверяют реальный номер колонки при пустых ячейках, неизвестные поля, связь исходной строки с импортированным пунктом, разбиение на две задачи, нескольких исполнителей и идемпотентный повтор.

Playwright на desktop и mobile проверяет сценарий с DOCX, русским именем файла, автоматическим заполнением полей, разбиением строки, назначением нескольких сотрудников, сохранением неизвестной колонки в комментарии и появлением обеих задач в календарном/рабочем контуре.
