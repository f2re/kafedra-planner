# Объектные права доступа — 0.1.0-rc.3

## Назначение

Роли `staff`, `manager` и `admin` определяют общий уровень полномочий, но не дают
доступ ко всем предметным данным рабочего пространства. Начиная с `rc.3`
документы, распоряжения и научные материалы дополнительно проходят единую
серверную объектную проверку.

## Безопасное правило по умолчанию

Новая загрузка получает:

- `access_scope = restricted`;
- владельца — сотрудника текущей серверной сессии;
- отсутствие неявного доступа для остальных сотрудников.

Администратор может явно сделать объект видимым всему рабочему пространству.
Обычный клиент не может назначить себе владельца или расширить область доступа
заголовками запроса.

Существующие материалы при миграции получают владельца, если его можно
однозначно вывести из связанного отчёта, поручения или автора научного материала.
Если владелец не определяется, объект остаётся `restricted` без владельца и
доступен только администратору до явного решения. Это сознательно безопаснее,
чем автоматически открыть старые документы всем сотрудникам.

## Роли объекта

| Роль | Чтение | Изменение | Контроль | Управление ACL |
|---|---:|---:|---:|---:|
| reader | да | нет | нет | нет |
| editor | да | да | нет | нет |
| controller | да | да | да | нет |
| owner | да | да | да | да* |
| admin | да | да | да | да |

`*` В `rc.3` изменение ACL через административный API оставлено за системной
ролью `admin`; роль `owner` используется как предметный уровень доступа и
подготовлена для последующего делегирования управления.

## Наследование

Права не размножаются в базе на каждого руководителя. Они вычисляются при
запросе из актуальной предметной модели.

Документ наследует отношения от:

- отчёта, приложенного к поручению;
- распоряжения и его исполнителей/контролирующих;
- научного материала и его авторов.

Распоряжение наследует отношения от поручений. Исполнитель получает чтение,
контролирующий — контроль. Руководитель получает `controller`, если объект
относится к любому сотруднику в его рекурсивной зоне управления.

Научный материал доступен связанному автору и его руководителям. При наличии
исходного документа может наследоваться право чтения этого документа.

## Единая точка проверки

Одна и та же политика применяется к:

- списку документов;
- карточке документа;
- оригиналу и предпросмотру;
- структурным блокам документа;
- исходнику и черновику шаблона;
- исправлению извлечённых полей;
- распоряжениям и поручениям;
- сопоставлению и подтверждению отчёта;
- научному реестру;
- полнотекстовому поиску;
- календарным записям, связанным с защищённым объектом;
- очереди проверки.

Таким образом знание идентификатора объекта или прямого URL не даёт обхода
списковой фильтрации.

## Ответ при запрете

Для существующего объекта без права доступа API возвращает HTTP `403` с общей
ошибкой `object_access_forbidden`. Ответ не содержит название, автора, имя файла,
контрольные суммы, путь blob-хранилища или другие метаданные объекта.

Отсутствующий объект возвращает `404`.

## Административный API

Получить объяснение текущей политики:

```text
GET /api/admin/access/document/<id>
GET /api/admin/access/directive/<id>
GET /api/admin/access/scientific_item/<id>
```

Заменить политику:

```text
PUT /api/admin/access/<kind>/<id>
X-CSRF-Token: <token текущей сессии>
Content-Type: application/json

{
  "ownerPersonId": "person-...",
  "accessScope": "restricted",
  "grants": [
    { "personId": "person-...", "role": "reader" },
    { "personId": "person-...", "role": "editor" }
  ]
}
```

Административный ответ показывает:

- владельца и область видимости;
- явные гранты;
- предметные связи, из которых система выводит динамический доступ.

Изменение записывается в `auth_audit_events` как `acl.object_updated`.

## Проверка релиза

Отдельный Chromium-сценарий запускается командой:

```bash
npm run test:browser:acl
```

Он проверяет цепочку:

```text
сотрудник
→ видит собственный документ
→ не видит чужой в списке
→ получает 403 по прямому URL оригинала
→ не получает чужой текст через поиск
→ не видит чужую научную карточку
→ руководитель видит объект подчинённого, но не постороннего
→ администратор выдаёт явный reader-грант
→ сотрудник получает доступ только после гранта
```

Этот сценарий входит в обязательный CI каждого push и pull request.
