# План развития

## Текущий рубеж — `0.3.4`

`0.3.4` — эксплуатационный release candidate, схема SQLite `30`. Основные рабочие контуры собраны в единую автономную систему:

- неизменяемые документы, версии, SHA-256, структурные локаторы и ручные ревизии;
- календарь, периодические задачи, сроки, уведомления и происхождение записей;
- распоряжения, поручения, исполнители, прогресс, отчёты и подтверждение;
- импортированные и ручные годовые планы, исходные строки/ячейки и разложение одной строки в несколько задач;
- точное автоматическое назначение ответственного без угадывания неоднозначных ФИО;
- связь `пункт плана → поручение → отчёт → План / факт`;
- обратимый архив документов, планов и шаблонов с impact summary и сохранением исторических источников;
- заседания, визуальная настройка обычных DOCX, версии шаблонов протоколов/выписок, тестовое заполнение и точная историческая версия;
- научный реестр, оргструктура, импорт и отчёты;
- необязательная интеграция Оформлятора с выбором пространства, группы и переносимых полей сотрудников;
- PIN, account mode, объектные ACL и аудит;
- backup/restore, атомарное обновление и rollback;
- full offline package contract `full-airgap-v2 / additive-only-v2`;
- необязательный `llama.cpp`, не влияющий на работоспособность deterministic-контура.

Стабильный релиз не объявляется до реальной эксплуатационной приёмки на Astra Linux/Debian по [`TARGET_ACCEPTANCE.md`](TARGET_ACCEPTANCE.md) и issue #27.

## R0 — платформенное основание

Состояние: завершено и покрыто регрессией.

- Node.js API и worker;
- SQLite/WAL и последовательные миграции;
- content-addressed blob-хранилище;
- устойчивая очередь и transactional outbox;
- FTS5, аудит и системная диагностика;
- автономная поставка без Docker/CDN.

Критерий: перезапуск не теряет данные и не требует ручного восстановления очереди.

## R0.6–R0.10 — рабочий цикл кафедры

Состояние: реализовано.

- основания и поручения;
- отчёты и подтверждение;
- научный реестр и отчётность;
- `План / факт`;
- импортированные и ручные планы;
- режимы `track / assigned / open`;
- сопроводительные документы;
- годовой DOCX без второго источника истины.

Критерий: обязательство проходит от источника до подтверждённого результата с сохранением истории и evidence.

## R0.11 — реальные строки плана и lifecycle

Состояние: реализовано.

- `plan_source_rows` хранит исходные таблицы, строки, ячейки, локаторы и неизвестные колонки;
- одна строка может стать несколькими обычными `plan_items`;
- для каждой задачи задаются собственные сроки, режим, исполнители и контролирующий;
- точное однозначное ФИО создаёт одно связанное поручение;
- неоднозначность не назначается автоматически;
- повторный materialize идемпотентен;
- документ и план архивируются обратимо, а логический преемник используется только для навигации;
- источник, календарь, поручения, отчёты и подтверждённые факты не перепривязываются.

## R0.12 — заседания и DOCX-шаблоны

Состояние: реализовано в schema `29`.

- обычный DOCX без маркеров превращается в шаблон через визуальное назначение полей и повторяемых блоков;
- профиль имеет draft/ready и привязан к точной версии исходника;
- библиотека разделяет протоколы и выписки, серии и последовательные версии;
- основной шаблон выбирается отдельно для каждого вида;
- тестовое заполнение двумя вопросами создаёт неизменяемый DOCX;
- PDF-preview через LibreOffice необязателен и не откатывает DOCX;
- старое заседание продолжает использовать свою точную версию;
- archive/restore сохраняет исходник, профили, заседания и сформированные документы.

Следующее развитие: расширение golden-корпуса сложных ведомственных DOCX, таблиц, колонтитулов и нестандартной нумерации без изменения пользовательского контракта.

## R0.13 — люди и Оформлятор

Состояние: реализовано в schema `30`.

- HTTP/HTTPS host/port и отдельные health/readiness/data проверки;
- краткоживущий код доступа без сохранения;
- выбор пространства и группы;
- preview ФИО до импорта;
- получение property definitions выбранного пространства;
- ФИО переносится всегда;
- e-mail и должность маппятся явно;
- дополнительные person-свойства выбираются отдельно и хранятся с remote property key;
- удалённое или переименованное поле вызывает конфликт до локальных изменений;
- идемпотентность по remote employee id;
- повторная синхронизация не удаляет локальную историю.

Следующее развитие: фоновая синхронизация только после реальной эксплуатации ручного сценария и отдельного решения по расписанию/политике конфликтов.

## R1 — безопасная эксплуатация

Состояние: программный контур реализован; целевая приёмка относится к R8.

- первый вход по четырёхзначному PIN;
- `scrypt`, временная блокировка, root-only reset;
- HttpOnly-сессии, CSRF, роли и объектные ACL;
- backup/restore, release evidence и rollback.

## R2 — операторская работа с документом

Состояние: основной сценарий реализован.

Следующее развитие: более точная навигация по большим PDF/таблицам, дополнительный golden-корпус реальных документов и понятные локальные инструменты исправления без уничтожения машинного результата.

## R3 — шаблоны и отчётные формы

Состояние: планы и заседания имеют рабочие versioned DOCX-контуры.

Следующее развитие:

- единый визуальный подход к годовым отчётным формам;
- выбираемые секции и поля без пользовательского кода;
- предварительная проверка результата;
- сохранение исходного DOCX и всех редакций профиля.

## R4 — организация и справочники

Состояние: подразделения, должности, периоды назначений, руководители, исполнители, историческая аффилиация и необязательный импорт Оформлятора реализованы.

Следующее развитие: дополнительные справочники только из подтверждённых эксплуатационных потребностей; не создавать универсальный low-code конструктор заранее.

## R5 — уведомления и поиск

Состояние: FTS5, фасеты, локальные уведомления, SMTP/Telegram adapters и дедупликация реализованы.

Следующее развитие: только существенные уведомления, объединение повторов и персональные правила без спама.

## R6 — локальное интеллектуальное обогащение

Состояние: необязательная OpenAI-compatible интеграция и offline `llama.cpp/GGUF` поставка реализованы.

Ограничение: LLM создаёт только кандидаты с источником; подтверждённые факты молча не заменяются. Отключение LLM не должно менять основной функционал.

## R7 — выпуск и сопровождение

Состояние: GitHub Release publisher, полный bundle, installer, Project Control package, контрольные суммы и no-op защита уже опубликованной версии реализованы.

Критерий: тег и все assets относятся к точному post-merge SHA; реальная job failure не скрывается повторным запуском.

## R8 — целевая эксплуатационная приёмка

Состояние: открыто, issue #27.

Необходимо документально подтвердить на реальной Astra Linux и контрольной Debian:

- чистую установку `0.3.4`;
- обновление `0.3.3 / schema 28` до `0.3.4 / schema 30`;
- первый PIN-flow;
- реальную обработку ведомственных DOCX/PDF/XLSX;
- сохранность данных после backup/restore;
- forced rollback;
- vendor package revisions, права каталогов и systemd hardening;
- desktop/mobile сценарии;
- при использовании — реальный Оформлятор и настоящий llama-server/GGUF.

Только после подписанного акта R8 допускается stable-метка.
