# Локальная защита доступа и роли

Штатный режим Kafedra Planner — простой локальный PIN-код. Он нужен как защита от случайного доступа к установленной системе: пользователю не требуется создавать аккаунт, придумывать логин или искать временный пароль.

Внутренняя модель ролей и объектных прав при этом сохраняется:

```text
PIN → внутренняя admin-сессия → серверные роли/ACL → предметные данные
```

Для организаций, которым действительно нужны отдельные персональные входы, остаётся явный расширенный режим `accounts`:

```text
локальный аккаунт → сотрудник → роль → предметные связи + объектная ACL
```

## Первый вход по PIN

При `KAFEDRA_AUTH_MODE=pin` — это режим по умолчанию — штатный installer автоматически гарантирует наличие внутренней учётной записи администратора, но не создаёт и не показывает пользователю реквизиты входа.

Первый запуск использует одно поле и два коротких шага:

1. открыть главную страницу Kafedra Planner;
2. придумать PIN из **4 цифр** — после четвёртой цифры интерфейс сам перейдёт к подтверждению;
3. в том же поле повторить эти четыре цифры;
4. после совпадения система автоматически сохраняет только параметризованный `scrypt`-хэш и открывает рабочий интерфейс.

Если второй ввод не совпал с первым, оба значения отбрасываются и интерфейс понятно начинает настройку заново. Первый PIN не сохраняется в DOM, `localStorage`, cookie или конфигурационном файле.

При следующих входах на экране есть только одно поле PIN. После ввода четвёртой цифры вход выполняется автоматически; кнопка «Открыть» остаётся доступной как обычный fallback. После неверного PIN поле очищается и сразу готово к следующему вводу.

Клиент трактует отсутствие `authMode` как штатный `pin`; поэтому старый или неполный ответ сервера не должен внезапно показывать форму логина/пароля. Username/password интерфейс создаётся только при явном серверном `authMode=accounts`.

После пяти неверных PIN-кодов вход блокируется на 15 минут. Сам PIN никогда не записывается в аудит, cookie или открытый конфигурационный файл.

## Смена и аварийный сброс PIN

Обычная смена выполняется из меню **«Доступ → Сменить PIN-код»**. Требуются текущий PIN, новый PIN и повтор нового PIN. После смены остальные активные сессии этого локального доступа завершаются.

Если PIN забыт, на установленной Astra Linux/Debian его можно заменить локально от `root` без знания прежнего PIN и без npm:

```bash
sudo /opt/kafedra-planner/current/scripts/reset-pin.sh
```

Скрипт дважды запросит новый четырёхзначный PIN без отображения ввода, безопасно прочитает `/etc/kafedra-planner/kafedra-planner.env`, обновит `scrypt`-хэш и завершит все прежние сессии. Исходные документы, роли, ACL и история работы не меняются.

Для source checkout доступна низкоуровневая команда с файлом секрета:

```bash
npm run auth:reset-pin -- --pin-file /root/kafedra-pin
```

## Роли и объектный доступ

Внутренняя модель не удаляется, потому что она используется серверными политиками, аудитом и расширенным многопользовательским режимом:

- `staff` — собственные поручения, отчёты, план/факт, уведомления и доступные объекты;
- `manager` — собственный контур плюс рекурсивная зона подчинённых/контролируемых обязательств;
- `admin` — административный доступ в пределах серверных политик.

Объектная ACL применяется дополнительно к роли. Прямой URL или производная запись не расширяет доступ к исходному объекту.

## Расширенный режим аккаунтов

Если на одной установке нужны отдельные входы сотрудников, явно задайте:

```text
KAFEDRA_AUTH_MODE=accounts
```

В этом режиме сохраняются прежние username/password API, роли `staff / manager / admin`, персональный контур и административное управление аккаунтами. Пароли хранятся как параметризованный `scrypt`-хэш с индивидуальной солью. Этот режим не является штатным для простой локальной установки.

Создание аккаунта из source checkout:

```bash
npm run auth:create-admin -- \
  --username admin \
  --person-name 'Иванов Иван Иванович' \
  --password-file /root/kafedra-admin-password
```

## Сессии и защита запросов

Сессия использует непрозрачный серверный токен; cookie имеет `HttpOnly`, `SameSite=Lax`, ограниченный срок и `Secure` при HTTPS-конфигурации. Изменяющие browser-запросы защищены CSRF. Первый `POST /api/auth/setup-pin` разрешён без CSRF только пока сессии ещё нет; повторная настройка после появления PIN отклоняется.

Основная конфигурация:

```text
KAFEDRA_AUTH_ENABLED=true
KAFEDRA_AUTH_MODE=pin
KAFEDRA_AUTH_COOKIE_NAME=kafedra_session
KAFEDRA_AUTH_SESSION_HOURS=12
KAFEDRA_AUTH_SECURE_COOKIES=false
KAFEDRA_AUTH_TRUST_PROXY=false
KAFEDRA_AUTH_CSRF_ENABLED=true
```

При HTTPS включается `KAFEDRA_AUTH_SECURE_COOKIES=true`. Proxy headers учитываются только при явном `KAFEDRA_AUTH_TRUST_PROXY=true`.

## API штатного PIN-режима

```text
GET  /api/auth/me
POST /api/auth/setup-pin
POST /api/auth/login          { pin }
POST /api/auth/change-pin
POST /api/auth/logout
```

`GET /api/auth/me` до входа возвращает `authMode=pin` и `pinConfigured`, поэтому браузер сам выбирает между первым заданием PIN и обычным входом.

В режиме `accounts` используются прежние account endpoints, включая `/api/auth/change-password` и `/api/admin/accounts*`.

## Инварианты доступа

- рабочее пространство и действующий субъект определяются серверной сессией;
- PIN не передаётся в URL и не хранится в открытом виде;
- `staff` не может читать чужой персональный контур в режиме аккаунтов;
- `manager` получает доступ по фактической иерархии/предметным связям, а не по клиентскому параметру;
- календарь, поиск, preview и скачивание оригинала применяют ту же объектную политику;
- роли, ACL, approve/return/delete относятся к `never-learn` и не получают learned defaults;
- значимые административные действия и события PIN-аутентификации аудируются без записи секрета.

Подробно об объектных политиках: [`OBJECT_ACCESS.md`](OBJECT_ACCESS.md). Производственная проверка: `npm run test:browser:auth` проверяет штатный PIN на desktop/mobile и legacy account regression; `npm run test:browser:acl` отдельно проверяет объектные права. На установленной системе используются штатный offline doctor и целевая приёмка.

## Режим разработки без авторизации

`KAFEDRA_AUTH_ENABLED=false` допустим только для разработки/части тестов. Production full bundle использует локальную защиту доступа по умолчанию.
