# Архитектура

## Границы системы

`kafedra-planner` — источник истины по документам, событиям, решениям, планам и деятельности. Он не должен дублировать генератор документов `docomator` и разбор расписаний `planer-solving`.

```text
Kafedra Planner
  ├─ документы и доказательства
  ├─ люди и подразделения
  ├─ планы работы и их пункты
  ├─ календарь и поручения
  ├─ заседания и решения
  ├─ наука и образование
  ├─ поиск и отчётные проекции
  └─ интеграционные API
       ├─ Docomator
       └─ Planner Solving
```

## Топология

```text
браузер
   │
   ▼
Node.js API ───────────────► SQLite + FTS5
   │                              ▲
   │                              │
   └── неизменяемые blob-файлы    │
                                  │
Node.js worker ───────────────────┘
   ├─ извлечение текста
   ├─ определение типа
   ├─ детерминированный предметный разбор
   ├─ шаблонный разбор
   ├─ календарные проекции
   └─ поисковая индексация
```

API и worker могут работать разными systemd-службами. Оба используют короткие транзакции. Worker арендует одно задание атомарным `BEGIN IMMEDIATE`; просроченная аренда позволяет продолжить обработку после аварийного завершения.

## Слои

### Платформа

- конфигурация;
- база и миграции;
- очередь;
- blob-хранилище;
- аудит;
- системная диагностика.

### Документы

- приём потока;
- SHA-256;
- определение формата;
- версии;
- нормализованный текст;
- структурные блоки и локаторы;
- адаптеры форматов.

### Предметные модули

- протоколы и заседания кафедры;
- планы и пункты планов;
- календарь;
- решения и поручения;
- наука и образование.

План является самостоятельной предметной сущностью. Исходная версия документа остаётся доказательством, `plan_items` содержат извлечённые пункты, а календарь и FTS являются производными проекциями. Контур `plan-fact` решает другую задачу — контроль фактического выполнения обязательств — и не подменяет модель планов.

Заседание также является самостоятельной предметной сущностью и может существовать до появления итогового файла протокола. `meeting_settings` хранит текущие параметры кафедры, а новое `meeting` получает снимок кворума, председателя, секретаря и версий DOCX-шаблонов. `agenda_items` образуют нумерованную повестку и при необходимости сохраняют `source_kind/source_id` исходного `plan_item` или календарной задачи. Сформированные протоколы и выписки регистрируются как обычные неизменяемые версии документов через `meeting_documents`, а не как временные файлы интерфейса.

### Проекции

- полнотекстовый поиск;
- календарь;
- обзор;
- очередь проверки;
- отчёты.

Проекция может быть пересоздана. Исходный документ и подтверждённые предметные записи не должны зависеть от поискового индекса.

## Транзакционные границы

Одна транзакция охватывает:

- регистрацию blob, документа, версии и задания;
- сохранение результата извлечения вместе с предметными сущностями, календарём, FTS, фасетами и вопросами проверки;
- закрытие пункта проверки;
- применение будущей операторской коррекции и создание ревизии.

Файловое сохранение завершается до регистрации версии. Файл имеет адрес по SHA-256 и поэтому безопасно переиспользуется после повторного запроса.

Для планов действует дополнительная идемпотентность: одна версия документа может породить не более одного `plan`, а пункт имеет устойчивый `source_item_key` по строке/ячейке источника. Повторная обработка завершённой версии не создаёт дубли календарных записей.

Для заседаний изменение повестки атомарно обновляет предметные записи и поисковую проекцию, а создание/изменение заседания поддерживает единственную календарную запись `source_kind=meeting`. Генератор DOCX сначала детерминированно строит файл и сохраняет content-addressed blob, затем одной транзакцией регистрирует `documents/document_versions`, `meeting_documents`, FTS и аудит. `request_hash` включает шаблон и фактическое состояние выбранных вопросов, поэтому одинаковый повторный запрос не создаёт второй документ.

## Происхождение

Каждая извлечённая запись должна содержать:

- `source_document_version_id` либо однозначную связь с ним;
- код и версию обработчика;
- локатор исходного фрагмента;
- уверенность;
- состояние подтверждения или проверки.

Структурный слой даёт локаторы абзацев и ячеек DOCX/ODT, листов и ячеек XLSX/ODS, строк текста, а для PDF — страницу и доступные координаты/строки текстового слоя.

Календарная проекция плана дополнительно хранит `origin_kind`, `origin_id`, человекочитаемую подпись источника, `origin_document_id` и локатор исходного пункта. Календарная запись не становится новым источником истины.

У вопроса заседания, созданного из плана или задачи, сохраняется явная ссылка на исходную предметную запись. Эта связь используется для обратного перехода из плана и не подменяет исходные данные: текст `Слушали/Обсудили/Решили` является отдельным фактом заседания. Сформированный протокол или выписка трассируются через `meeting_documents` к заседанию и точному набору номеров вопросов.

## Доступ к производным объектам

Производная сущность не должна расширять доступ к исходному документу.

Для `plan` и `plan_item` API сначала разрешает доступ к исходному документу. Календарные события, задачи и уведомления с `source_kind=plan_item` наследуют те же права. FTS-фрагменты планов содержат `document_version_id`, поэтому существующая фильтрация поиска также проверяет доступ к исходному документу.

Это правило следует применять и к будущим производным проекциям документов.

## Расширение новым типом документа

1. Добавить детектор типа.
2. Определить декларативный контракт результата.
3. Реализовать детерминированный extractor.
4. Добавить persistence service.
5. Добавить golden fixtures.
6. Определить создаваемые календарные и поисковые проекции.
7. Определить наследование ACL от исходного объекта.
8. Определить вопросы, которые должны поступать оператору.
9. Подключить обработчик в worker без разрушения существующих маршрутов.
10. Добавить unit/integration и сквозной тест повторной обработки.

Явно выбранный оператором тип документа имеет приоритет над автоэвристикой. Автодетектор не должен классифицировать документ только потому, что название другого типа встретилось внутри таблицы, результата или приложения.

## Архитектурные запреты

- выполнение пользовательского JavaScript;
- запись в каталог активной версии приложения;
- изменение исходного файла;
- факт без ссылки на источник;
- удаление истории при исправлении;
- прямой доступ `docomator` и `planer-solving` к базе;
- обязательная внешняя модель ИИ;
- сетевые CDN и установка npm-пакетов на целевой машине;
- блокирование пакета одним неразобранным документом;
- техническая ошибка без предлагаемого оператору действия;
- выдача производной сущности пользователю, которому недоступен исходный документ.
