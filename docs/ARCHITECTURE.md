# Архитектура

## Границы системы

`kafedra-planner` — источник истины по документам, событиям, решениям и деятельности. Он не должен дублировать генератор документов `docomator` и разбор расписаний `planer-solving`.

```text
Kafedra Planner
  ├─ документы и доказательства
  ├─ люди и подразделения
  ├─ календарь и поручения
  ├─ планы и план/факт
  ├─ заседания и решения
  ├─ наука и образование
  ├─ поиск и отчётные проекции
  └─ интеграционные API
       ├─ Docomator
       └─ Planner Solving
```

## Топология

```text
браузер
   │
   ▼
Node.js API ───────────────► SQLite + FTS5
   │                              ▲
   │                              │
   └── неизменяемые blob-файлы    │
                                  │
Node.js worker ───────────────────┘
   ├─ извлечение текста и структуры
   ├─ определение типа
   ├─ детерминированный предметный разбор
   ├─ календарные проекции
   └─ поисковая индексация
```

API и worker могут работать разными systemd-службами. Оба используют короткие транзакции. Worker арендует одно задание атомарным `BEGIN IMMEDIATE`; просроченная аренда позволяет продолжить обработку после аварийного завершения.

## Контур планов

План — отдельная предметная сущность, а не разновидность `plan-fact`. `plans` и `plan_items` описывают утверждённый источник мероприятий и сроков; `plan-fact` отвечает за последующий контроль исполнения и фактические показатели.

```text
исходный DOCX/XLSX/PDF
        │
        ▼
document_version + document_blocks
        │
        ▼
детерминированный plan extractor
        │
        ├──► plan + plan_items + evidence
        ├──► FTS5 + facets
        ├──► review_items при неоднозначности
        └──► calendar_items(source_kind = plan_item)
```

Поддерживаются планы кафедры, факультета, подразделения, организации и личные планы. Для личного плана владелец является частью предметной записи; API фильтрует как сам план, так и его проекции в общем календаре по пользователю и иерархии руководителя.

Календарная запись из плана не является новым источником истины. Она хранит ссылку на `plan_item`, а пункт — доказательство по строке/ячейке исходной версии документа. Поэтому календарь можно пересоздать, не теряя основание.

## Формирование плана по DOCX-образцу

Шаблон формирования плана хранит ссылку на неизменяемый исходный DOCX, вид плана, тип периода, найденный токен года, номер таблицы, строку заголовка, строку-образец и карту столбцов. Настройка версионируется.

При формировании:

1. год или учебный год нормализуется;
2. исходный DOCX читается как OOXML;
3. значение года заменяется только в текстовых узлах документа;
4. строка-образец таблицы клонируется для каждого пункта, поэтому её стили и свойства сохраняются;
5. сформированный DOCX сохраняется как новый неизменяемый документ;
6. он проходит тот же штатный worker-разбор, что и загруженный план.

Генератор использует стандартные модули Node.js и системный `unzip`; новая обязательная runtime-зависимость не вводится. Ключ запроса и хэш полезной нагрузки обеспечивают идемпотентность повторного формирования.

## Транзакционные границы

Одна транзакция охватывает:

- регистрацию blob, документа, версии и задания;
- сохранение результата извлечения вместе с заседанием, пунктами, решениями, планами, календарём и вопросами проверки;
- регистрацию сформированного документа, связи с шаблоном и подсказок его повторного разбора;
- закрытие пункта проверки;
- применение операторской коррекции и создание ревизии.

Файловое сохранение завершается до регистрации версии. Файл имеет адрес по SHA-256 и поэтому безопасно переиспользуется после повторного запроса.

## Происхождение

Каждая извлечённая запись должна содержать:

- `source_document_version_id` либо однозначную связь с сущностью, которая его содержит;
- код и версию обработчика;
- локатор исходного фрагмента;
- уверенность;
- состояние подтверждения или вопрос оператору при неоднозначности.

Планы используют существующие `document_blocks`: ячейки DOCX/ODT/XLSX и текстовые строки становятся доказательством конкретного пункта. Ручное исправление не должно уничтожать машинный результат или исходный документ.

## Расширение новым типом документа

1. Добавить детектор типа.
2. Определить декларативный контракт результата.
3. Реализовать детерминированный extractor.
4. Добавить persistence service.
5. Добавить golden fixtures.
6. Определить создаваемые календарные и поисковые проекции.
7. Определить вопросы, которые должны поступать оператору.
8. Подключить обработчик в dispatcher без изменения базового конвейера документов.

## Архитектурные запреты

- выполнение пользовательского JavaScript;
- запись в каталог активной версии приложения;
- изменение исходного файла;
- факт без ссылки на источник;
- удаление истории при исправлении;
- прямой доступ `docomator` и `planer-solving` к базе;
- обязательная внешняя модель ИИ;
- сетевые CDN и установка npm-пакетов на целевой машине;
- блокирование пакета одним неразобранным документом;
- техническая ошибка без предлагаемого оператору действия.
