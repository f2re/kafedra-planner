# Архитектура

## Границы системы

`kafedra-planner` — автономный источник истины по документам, планам, календарю, поручениям, заседаниям и деятельности кафедры. Универсальное редактирование документов остаётся задачей `docomator`, а разбор учебных расписаний — `planer-solving`.

Система полностью работает без Интернета и LLM. Локальный `llama.cpp` допускается только как необязательный источник кандидатов; факт без подтверждённого источника не создаётся.

```text
браузер
   │
   ▼
Node.js API ───────────────► SQLite + FTS5
   │                              ▲
   ├── неизменяемые blob-файлы    │
   │                              │
Node.js worker ───────────────────┘
   ├─ извлечение текста и структуры
   ├─ определение типа документа
   ├─ детерминированный предметный разбор
   ├─ локальный preview/OCR при наличии
   ├─ календарные и поисковые проекции
   └─ необязательные LLM-кандидаты
```

API и worker — отдельные systemd-службы, работающие с одной SQLite в WAL-режиме. Worker арендует задания атомарно; ошибка одного документа не блокирует очередь.

## Слои

Платформа отвечает за конфигурацию, SQLite и миграции, blob-хранилище, очередь, аудит, backup/restore, обновление и rollback.

Документный слой принимает DOCX/ODT/XLSX/ODS/PDF/text, сохраняет SHA-256 blob и неизменяемые `document_versions`, извлекает нормализованный текст и `document_blocks` с локаторами. Файл физически сохраняется до предметной регистрации; повтор может безопасно переиспользовать content-addressed blob.

Предметные модули хранят подтверждённое состояние: планы, поручения, заседания, научные материалы, сопроводительные документы. Календарь, FTS, фасеты, обзор и уведомления — перестраиваемые проекции.

## Планы: источник → строка → задача

Импортированный `plan` (`origin_kind=document`) ссылается на неизменяемую `document_version`. Ручной `plan` (`origin_kind=manual`) не получает фиктивный источник.

Для реального импортированного плана введён промежуточный слой:

```text
document_version
  └─ document_blocks
       └─ plan_source_rows
            ├─ raw cells + labels + locators
            ├─ deterministic suggestion
            ├─ unmapped values
            └─ 0..N plan_items
```

`plan_source_rows` не является второй копией Word-документа. Это устойчивый индекс исходной строки для проверки происхождения и повторяемого разложения. Сама версия документа и структурные блоки остаются первичным доказательством.

`plan_source_row_items` фиксирует, какие подтверждённые пункты созданы из строки и их `split_index`. Один source row может дать несколько `plan_items`; один `plan_item` принадлежит не более чем одной исходной строке. Это позволяет разложить составной пункт на несколько сроков и исполнителей без изменения существующей модели поручений.

Существующие импортированные планы получают source rows лениво из сохранённых `document_blocks`. Повторная загрузка файла не нужна. Новые импорты сохраняют source rows в той же транзакции, что и план и автоматически распознанные пункты.

Детерминированный табличный разбор использует реальные номера колонок. Пустая промежуточная ячейка не должна сдвигать дату в поле ответственного. Неизвестная колонка сохраняется с подписью заголовка; оператор может оставить её в комментарии задачи.

Подробности: [`PLAN_SOURCE_ROWS.md`](PLAN_SOURCE_ROWS.md).

## Планы и календарь

`plan_items` имеют происхождение `extracted | manual` и режим исполнения `track | assigned | open`. Извлечённый пункт хранит evidence и локатор, ручной — автора, время и manual provenance.

Календарь не является вторым источником истины. `calendar_items` с `source_kind=plan_item` пересобираются после предметного изменения. Исправление пункта обновляет календарь, поиск, фасеты и вопросы проверки.

Одна исходная строка, разделённая на две задачи, создаёт две независимые календарные проекции. Повтор materialize той же строки использует стабильные `split_index` и не создаёт дубли.

## Мост `plan_item → assignment`

Кардинальность не меняется:

- `track` — только событие/контрольный срок;
- `assigned` — единственное формальное поручение;
- `open` — единственное поручение, которое можно атомарно принять в работу.

`plan_item_assignments` уникален в обе стороны. Несколько исполнителей находятся внутри обычного `assignment` через `assignment_executors`. Поэтому «одна строка плана → несколько задач → несколько сотрудников» моделируется несколькими `plan_items`, а не усложнением моста.

Поручение из плана может не иметь `directive_id`; оно использует общий контур прогресса, отчётных доказательств, подтверждения руководителем и `План / факт`.

Система не удаляет уже созданное поручение молча при переключении пункта в `track` и не уничтожает дополнительные задачи, если оператор повторно сохранил меньше частей исходной строки.

## Сопроводительные документы

`supporting_documents` — самостоятельные номерные сущности. Номер и дата обязательны, файл необязателен. `supporting_document_links` связывает их с документом, пунктом плана, поручением, научным материалом или заседанием. Отвязка удаляет только связь; документ, реквизиты и аудит остаются.

## Заседания и наука

`meeting` существует независимо от итогового протокола. Повестка может ссылаться на пункты плана и календарные задачи. Сформированные протоколы/выписки проходят обычный document intake.

Научный реестр и отчётные контуры используют те же правила происхождения: автоматический факт хранит доказательство, ручное исправление не уничтожает исходное значение.

## Доказательства

Каждый автоматически извлечённый факт имеет однозначную связь с `document_version`, локатор, код/версию обработчика, уверенность и состояние проверки. Source row дополняет доказательство, но не заменяет его.

Ручное изменение не перезаписывает исходный `evidence_json`. История хранится в audit/revision-контуре. Неизвестное значение из таблицы не отбрасывается только потому, что системе не известен его предметный тип.

## Доступ

Производная сущность не расширяет ACL источника. Импортированный план наследует права документа, ручной получает собственную объектную политику. Исполнитель поручения не получает автоматически весь закрытый план. Source rows используют тот же `assertPlanAccess`, что и план.

Подробности: [`AUTHORIZATION.md`](AUTHORIZATION.md), [`OBJECT_ACCESS.md`](OBJECT_ACCESS.md).

## Транзакции и идемпотентность

Логически неделимые операции выполняются транзакционно: регистрация документа, сохранение результатов извлечения, materialize source row, создание/обновление поручения, принятие open-задачи, создание сопроводительного документа и подтверждение отчёта.

Критические повторяемые запросы используют idempotency key или устойчивые уникальные ключи. Source row использует `(plan_id, source_row_key)`, а разложенные задачи — `(source_row_id, split_index)`. Повтор не создаёт второй план, пункт, поручение или файл.

## Ошибки и UX

- ошибка одного файла/строки не блокирует остальные;
- неоднозначность показывается там, где оператор её исправляет;
- введённые значения не очищаются после ошибки;
- исходный документ доступен рядом с производными данными;
- технические WebIDL/SQLite сообщения не должны попадать пользователю;
- автоматически определяемые значения не спрашиваются повторно;
- основные действия остаются доступными на desktop и mobile.

## Backup, обновление и rollback

Release gate проверяет `quick_check`, `foreign_key_check`, blob-хэши, backup/restore, историю и rollback. `plan_source_rows` и `plan_source_row_items` — устойчивые предметные таблицы и должны входить в логические digest наряду с `plans`, `plan_items` и `plan_item_assignments`.

Schema 26 аддитивна: существующие планы, пункты, документы, поручения и история не переписываются.

## Архитектурные запреты

- изменение или уничтожение исходного файла;
- автоматически созданный факт без доказательства;
- обязательный внешний сервис, CDN, Docker или LLM;
- пользовательский JavaScript в шаблонах;
- прямой доступ интеграций к SQLite;
- расширение ACL через производную запись;
- скрытое удаление поручения или уже созданной задачи;
- блокирование очереди одним документом;
- npm-установка на целевой автономной машине;
- сообщение об успехе до фактической фиксации данных.
