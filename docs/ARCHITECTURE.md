# Архитектура

## Границы системы

`kafedra-planner` — источник истины по документам, событиям, решениям и деятельности. Он не должен дублировать генератор документов `docomator` и разбор расписаний `planer-solving`.

```text
Kafedra Planner
  ├─ документы и доказательства
  ├─ люди и подразделения
  ├─ календарь и поручения
  ├─ заседания и решения
  ├─ наука и образование
  ├─ поиск и отчётные проекции
  └─ интеграционные API
       ├─ Docomator
       └─ Planner Solving
```

## Топология

```text
браузер
   │
   ▼
Node.js API ───────────────► SQLite + FTS5
   │                              ▲
   │                              │
   └── неизменяемые blob-файлы    │
                                  │
Node.js worker ───────────────────┘
   ├─ извлечение текста
   ├─ определение типа
   ├─ шаблонный разбор
   ├─ календарные проекции
   └─ поисковая индексация
```

API и worker могут работать разными systemd-службами. Оба используют короткие транзакции. Worker арендует одно задание атомарным `BEGIN IMMEDIATE`; просроченная аренда позволяет продолжить обработку после аварийного завершения.

## Слои

### Платформа

- конфигурация;
- база и миграции;
- очередь;
- blob-хранилище;
- аудит;
- системная диагностика.

### Документы

- приём потока;
- SHA-256;
- определение формата;
- версии;
- нормализованный текст;
- адаптеры форматов.

### Предметные модули

- протоколы;
- календарь;
- решения и поручения;
- дальнейшие модули науки и образования.

### Проекции

- полнотекстовый поиск;
- календарь;
- обзор;
- очередь проверки;
- отчёты.

Проекция может быть пересоздана. Исходный документ и подтверждённые предметные записи не должны зависеть от поискового индекса.

## Транзакционные границы

Одна транзакция охватывает:

- регистрацию blob, документа, версии и задания;
- сохранение результата извлечения вместе с заседанием, пунктами, решениями, календарём и вопросами проверки;
- закрытие пункта проверки;
- применение будущей операторской коррекции и создание ревизии.

Файловое сохранение завершается до регистрации версии. Файл имеет адрес по SHA-256 и поэтому безопасно переиспользуется после повторного запроса.

## Происхождение

Каждая извлечённая запись должна содержать:

- `source_document_version_id`;
- код и версию обработчика;
- локатор исходного фрагмента;
- уверенность;
- состояние подтверждения.

Текущий протокольный обработчик использует диапазоны строк нормализованного текста. Для визуального редактора локатор будет расширен до абзацев DOCX, ячеек XLSX и координат PDF.

## Расширение новым типом документа

1. Добавить детектор типа.
2. Определить декларативный контракт результата.
3. Реализовать детерминированный extractor.
4. Добавить persistence service.
5. Добавить golden fixtures.
6. Определить создаваемые календарные и поисковые проекции.
7. Определить вопросы, которые должны поступать оператору.
8. Подключить обработчик в dispatcher без изменения маршрутов API.

## Архитектурные запреты

- выполнение пользовательского JavaScript;
- запись в каталог активной версии приложения;
- изменение исходного файла;
- факт без ссылки на источник;
- удаление истории при исправлении;
- прямой доступ `docomator` и `planer-solving` к базе;
- обязательная внешняя модель ИИ;
- сетевые CDN и установка npm-пакетов на целевой машине;
- блокирование пакета одним неразобранным документом;
- техническая ошибка без предлагаемого оператору действия.
