# Профили дополнительного распознавания протоколов

Статус: механизм R8. Полная приёмка на реальном повторяющемся формате остаётся в Issue #326 до появления двух обезличенных реальных протоколов одного вида.

## Зачем нужен профиль

Базовый `department-protocol` parser остаётся основным и детерминированным: он распознаёт номер, дату, участников, повестку и решения без LLM. Профиль не заменяет parser и не создаёт второй рабочий объект. Он используется только как дополнительный слой для устойчивого кафедрального формата, в котором нужный реквизит подписан иначе или есть дополнительные локальные поля.

Профилем служит существующий активный `document_template` с `document_type = department_protocol`. Поэтому отдельной таблицы, миграции и нового form-builder нет. Matcher и поля задаются тем же контрактом шаблонов (`requiredPhrases`, `filenameContains`, anchor/locator и тип значения).

## Приоритет и происхождение

Порядок значений:

1. уже извлечённый базовым parser реквизит;
2. профиль, если базовый parser оставил канонический реквизит пустым;
3. ручное рабочее значение всегда сохраняется при последующей обработке.

Профиль может дополнять `protocolNumber`, `meetingDate`, `chairperson`, `secretary`, `attendees`. Для русских шаблонных ключей поддерживаются явные узкие aliases: `nomer_protokola`, `data_zasedaniya`, `data_protokola`, `predsedatel`, `predsedatelstvoval`, `sekretar`, `prisutstvuyuschie`, `prisutstvovali`. Широкие ключи вроде `date` или `number` намеренно не угадываются.

Каждое профильное поле сохраняется в `extraction_run.result_json.protocol.profileFields` вместе с `document_version`, template id/version и evidence locator. Если канонический реквизит был дополнен в рабочем заседании, его locator также добавляется в `meeting.evidence_json.profileFields`. Исходный blob, SHA-256 и `document_version` не меняются.

Дополнительные профильные поля, которые не отображаются на канонический реквизит заседания, остаются машинными фактами в `profileFields` с тем же locator и не превращаются автоматически в подтверждённое рабочее поле.

## Конфликты и повторная обработка

Если базовый parser и профиль дают разные непустые значения, базовый результат не перезаписывается: создаётся review-by-exception с обоими вариантами и evidence.

Если оператор уже исправил рабочий реквизит, reprocess создаёт новый `extraction_run` для той же immutable `document_version`. Профиль снова сохраняет своё машинное значение и locator в новом run, но рабочая ручная правка остаётся без изменений; расхождение становится review. Старый extraction run не переписывается.

Ошибка одного дополнительного profile-template локальна: базовый протокол, исходник и успешные поля других профилей остаются доступными. Документ может перейти в `needs_review`, но не в `failed` только из-за ошибки дополнительного профиля.

LLM для этого механизма не используется и не требуется.

## Regression evidence и реальная приёмка

`tests/fixtures/protocol-profile-synthetic-1.txt` и `protocol-profile-synthetic-2.txt` — намеренно синтетическая пара одного формата. Она доказывает контракт 0/1 конфликтов, locator, reprocess и partial failure, но не качество распознавания реальных кафедральных документов.

Полная приёмка R8 выполняется только после добавления двух обезличенных реальных документов одного повторяющегося формата: профиль должен извлечь заданный реквизит в обоих документах, сохранить точные locators, пережить ручную коррекцию и reprocess без изменения immutable source. До этого Issue #326 остаётся открытым.
