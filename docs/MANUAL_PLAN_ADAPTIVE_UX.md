# Адаптивное заполнение ручного пункта плана

Этот документ уточняет общий контракт [`ADAPTIVE_UX.md`](ADAPTIVE_UX.md) для формы создания и редактирования ручного `plan_item`. Источником истины остаются `plan` и `plan_item`; пользовательские предпочтения лишь сокращают повторный ввод и не создают предметные факты.

## Пользовательский сценарий

При добавлении нового мероприятия система может заранее предложить:

- направление;
- режим исполнения: контрольная точка, поручение или открытая задача;
- основного исполнителя;
- контролирующего;
- начало, окончание и контрольный срок как относительные смещения.

Основной исполнитель выбирается отдельно от соисполнителей. При сохранении существующий API получает прежний массив `executorPersonIds`, где основной исполнитель идёт первым; backend, уникальный мост `plan_item → assignment` и идемпотентность не меняются.

Если у выбранного сотрудника однозначно известен руководитель из актуальной оргструктуры, он подставляется как контролирующий. Эта `domain-derived` автоматика сильнее статистического значения. После явного выбора другого контролирующего система больше не заменяет его при смене исполнителя.

## Приоритеты

Значение определяется в следующем порядке:

1. сохранённое поле существующего пункта;
2. явный контекст текущего действия, включая дату перехода из календаря;
3. руководитель исполнителя из оргструктуры;
4. наиболее частый персональный `safe-default`;
5. статический безопасный fallback формы.

При редактировании существующего пункта частота влияет только на порядок вариантов (`rank-only`) и не подменяет сохранённые значения.

## Даты

Абсолютные даты не запоминаются. Используются только значения `d:N` относительно понятной базовой даты либо `none`:

- `plan.item.start_offset` — относительно текущего дня;
- `plan.item.end_offset` — относительно выбранного начала, иначе текущего дня;
- `plan.item.due_offset` — относительно выбранного начала, иначе текущего дня.

Дата, переданная из календаря, всегда сохраняет приоритет над learned offset. Допустимый диапазон на сервере ограничен ±1095 дней.

## Разрешённые контексты

| Контекст | Класс | Назначение |
|---|---|---|
| `plan.item.direction` | `safe-default` при создании, `rank-only` при редактировании | Направление мероприятия |
| `plan.item.execution_mode` | `safe-default` / `rank-only` | Контрольная точка, поручение или открытая задача |
| `plan.item.executor` | `safe-default` / `rank-only` | Основной исполнитель |
| `plan.item.controller` | `safe-default` / `rank-only` | Контролирующий при отсутствии однозначного руководителя |
| `plan.item.start_offset` | `safe-default` | Относительное начало |
| `plan.item.end_offset` | `safe-default` | Относительное окончание |
| `plan.item.due_offset` | `safe-default` | Относительный контрольный срок |

Название, описание, ожидаемый результат и другие поля свободного делового текста относятся к `never-learn`.

## Когда статистика изменяется

Выбор записывается в существующий `ui_choice_preferences` только после успешного `POST/PATCH` пункта и только если человек действительно изменил контрол trusted-событием. Программно подставленные значения, learned defaults, руководитель из оргструктуры и дата из календаря частоту не увеличивают.

Один `interactionId` не может увеличить частоту повторно. Ошибка preference API не блокирует сохранение пункта. В режиме без авторизации используется тот же совместимый локальный fallback `kafedra-ui-preferences-v2`; отдельный механизм или второй источник настроек не создаётся.

## Проверки

Unit-тест подтверждает allowlist, person/date validation и идемпотентность `interactionId`. Playwright desktop/mobile проверяет:

- применение безопасных defaults к новому пункту;
- приоритет руководителя из оргструктуры над частым контролирующим;
- отсутствие обучения при простом сохранении программных подстановок;
- обучение только явно изменённых направления, исполнителя и относительного срока;
- сохранение значений существующего пункта;
- приоритет даты перехода из календаря.
