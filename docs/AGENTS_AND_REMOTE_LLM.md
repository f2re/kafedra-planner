# Промпты, запросы и диагностика локальной LLM

Kafedra Planner передаёт системный промпт и контекст в каждом запросе к OpenAI-совместимому `llama-server`. Модель может работать на том же компьютере или на отдельном узле локальной сети. Для добавления задачи достаточно обновления приложения: загружать промпты в веса GGUF или перезапускать сервер модели не требуется.

LLM остаётся необязательной. Без неё импорт сохраняет исходные документы и выполняет обычный разбор, подбор мероприятий использует правила, а оператор может составить и выгрузить месячный план вручную.

## Исполняемые задачи планов

| Задача и источник | Как запускается | Вход и результат |
| --- | --- | --- |
| [`plan-extract-v1`](../packages/ai/src/plan-task.mjs) | Обработка загруженного плана ставит фоновое задание `enrich_plan`; его исполняет [worker](../apps/worker/src/plan-llm-job.mjs) | Исходные строки и подтверждённый период → предложения мероприятий с `sourceRowKey`, цитатой, названием, исходными сроками, исполнителем, результатом и видом деятельности |
| [`plan-department-selection-v1`](../packages/ai/src/plan-selection-task.mjs) | Кнопка подбора в месячном плане → `POST /api/plan-events/suggest` → [сервис подбора](../packages/plans/src/selection.mjs) | Кафедра, месяц, определения полей и доступные мероприятия → `recommended` / `review` / `other`, объяснение, цитата и предложения для пустого места или дополнительных полей |

Это два действующих запроса приложения. Промпты и JSON Schema находятся в указанных модулях; каталог поставки берёт их оттуда вместе с параметрами, сформированными настоящими `preparePlanTask` и `prepareSelectionTask`.

Модель получает данные, а не права записи. Текст документов, названия кафедры и описания полей обозначены в промптах как недоверенные данные. Запросы не предоставляют инструменты. В обоих контурах используются `temperature: 0`, `stream: false`, `chat_template_kwargs.enable_thinking: false` и `response_format: { type: "json_object", schema: ... }`.

Перед применением сервер проверяет известные идентификаторы, допустимые поля и типы, непрерывные цитаты в конкретной строке или фрагменте. Даты преобразуются локальным парсером. Подбор не создаёт мероприятий и не изменяет их название, сроки, исполнителей или выполнение. Место и дополнительные значения нельзя вывести только из заголовка всего плана или записать поверх ручных данных.

Институтский источник не исключается целиком: в нём могут быть мероприятия кафедры. Модель оценивает конкретные пункты, а интерфейс показывает основание решения. Наличие цитаты подтверждает происхождение текста, но не гарантирует правильность смысловой классификации. Решение о включении и предложенные поля проверяет оператор.

## Ограничения запросов, настройки и восстановление

Обе задачи делят вход на группы не более шести строк или мероприятий. Ответ ограничен 2048 токенами и 65536 байтами. Консервативный бюджет входа учитывает `KAFEDRA_LLM_CONTEXT_SIZE` и размер ответа; целая слишком длинная строка исключается из LLM-запроса с диагностикой, её исходный текст сохраняется. Скрытого обрезания данных нет.

На HTTP 400/422 выполняется одна совместимая попытка без `response_format`, в пределах того же срока ожидания. Полученный JSON всё равно проходит серверную проверку. Незавершённый ответ, вызов инструмента, отказ, неизвестные идентификаторы и неподтверждённые поля не становятся подтверждёнными фактами. При частичной ошибке сохраняются проверенные предложения, остальные мероприятия остаются доступны через обычные правила и ручной выбор.

Административные настройки `enabled`, endpoint, model, API key, timeout и max tokens сохраняются в `llm-settings.json`. Подбор читает их при новом запросе, worker — при постановке и выполнении задания. Для следующего вызова перезапуск Planner не нужен. Размер контекста задаётся окружением процесса и не является редактируемой настройкой этого экрана; его изменение требует обычного перезапуска соответствующего процесса.

Смена настроек не перезапускает уже завершившиеся задания автоматически. Для повторного обогащения импортированного плана используется штатная повторная обработка исходного документа; она повторяет неудачные задания и учитывает текущую конфигурацию. Кнопка **«Обновить разбор»** в исходных строках только перечитывает результат фоновой обработки. Новый подбор месячного плана запускается кнопкой подбора.

История разбора хранится в `llm_extraction_runs`: версия документа, модель, версия промпта, хеш входа, состояние, результат и диагностические метаданные. Предложения остаются отдельно от принятых пунктов. Подбор сохраняется в `plan_event_selection_runs` с версией шаблона, снимками источников, их хешами и локаторами. Перед применением повторно проверяются доступ, актуальность источника и ревизия состава. Принятие использует сохранённый серверный результат, а не присланные клиентом цитаты. Связанный контракт: [шаблоны мероприятий](EVENT_TEMPLATES.md) и [несколько планов → план на месяц](MULTILEVEL_PLANS.md).

## Каталог промптов в поставке

[`task-catalogue.mjs`](../packages/ai/src/task-catalogue.mjs) объединяет 13 режимов из [`assistant-tasks.mjs`](../packages/ai/src/assistant-tasks.mjs) и две задачи планов. В текущем каталоге **15 задач**. Другие специализированные контуры, например разбор поручений и поисковая диагностика, сохраняют собственные модули и проверки; число 15 не обозначает число всех вызовов LLM в приложении.

[`department-agents.json`](../packages/ai/department-agents.json) содержит для каждой задачи:

- `id`, назначение и путь к исполняемому модулю;
- `promptVersion` для версионированных задач и `systemSha256` точного системного промпта;
- `systemPrompt`, `responseSchema`, лимиты и параметры HTTP-запроса в `request`;
- искусственный диагностический `sampleInput`, отделённый от рабочих данных кафедры.

У двух задач планов `responseSchema` совпадает с `request.options.response_format.schema` и с исполняемой схемой. Каталог воспроизводим: сборка не добавляет время генерации и не меняет его без изменения содержимого. Regression проверяет отсутствие расхождения с исходными промптами и запросами.

Для обновления отслеживаемого в Git каталога после изменения задачи:

```bash
node scripts/export-agent-prompts.mjs
```

Путь определяется относительно самого скрипта, поэтому команда не зависит от текущего рабочего каталога. Для отдельной выгрузки администратору:

```bash
node scripts/export-agent-prompts.mjs --output-dir /tmp/kafedra-llm-catalogue
```

В указанном каталоге появляются ровно три файла: `department-agents.json`, исполняемый `test-remote-agents.sh` и `AGENTS_GUIDE.md`. Этот режим не переписывает исходный каталог приложения. Неявного копирования в чужие проекты или на USB нет.

Штатные runtime/full-сборщики приложения включают `packages`, `apps`, `scripts`, `public` и migrations целиком: промпты, схемы, валидаторы и UI попадают в пакет вместе с реализацией. Отдельный каталог полезен для диагностики узла LLM; приложение не загружает промпты из этого каталога на удалённом сервере.

## Автономная проверка запросов

Для `test-remote-agents.sh` нужны **bash и Python 3 со стандартной библиотекой**. Дополнительные pip/npm-пакеты не требуются. Это зависимость отдельной диагностики, а не новая зависимость Planner. Реализации для Node в этом скрипте нет.

```bash
cd /tmp/kafedra-llm-catalogue
./test-remote-agents.sh --list
export LLM_ENDPOINT=http://127.0.0.1:8081
export LLM_MODEL=department-assistant
./test-remote-agents.sh plan-extract-v1
./test-remote-agents.sh plan-department-selection-v1
```

`LLM_API_KEY` задаёт необязательный Bearer token, `LLM_TIMEOUT` — общий срок одного запроса с возможной повторной попыткой, в секундах (по умолчанию 45). `AGENTS_FILE` указывает конкретный каталог. Endpoint допускает корень сервера или суффикс `/v1`; перенаправления запрещены. Без аргументов и с `--list` скрипт показывает задачи, не обращаясь к сети. `--all` последовательно проверяет задачи чата. `--embeddings` отдельно проверяет числовой вектор через `EMBED_ENDPOINT`, `EMBED_MODEL` и необязательный `EMBED_API_KEY`.

HTTP 200 сам по себе не считается успехом. Диагностика проверяет envelope, завершение `stop`, JSON, объявленную схему, а для двух задач планов — известные идентификаторы и цитаты из диагностического входа. Пустой результат этих двух искусственных примеров не проходит. Поддерживается только используемый поднабор JSON Schema: `type`, `properties`, `required`, `additionalProperties`, `items`, пределы длины/числа элементов и `enum`. Неизвестное свойство схемы останавливает проверку до HTTP.

Сообщение `PASS — запрос и контракт ответа` относится к ограниченному примеру. Оно не доказывает качество GGUF на документах кафедры, полноту разбора, работу OCR или правильность всех решений о принадлежности. Автоматический regression скрипта использует настоящий локальный HTTP-сервер с фиксированными ответами; это проверка транспорта и контрактов, **не запуск языковой модели**.

## Переносимый пакет для администратора LLM

```bash
npm run bundle:patch:llm
```

Сборщик формирует пакет каталога, диагностики и документации с метаданными исходного коммита и контрольными суммами. Он использует явный staging-каталог экспортёра. Подробный состав и проверка описаны в README внутри полученного пакета. Этот комплект можно распаковать на узле LLM и запустить диагностические команды выше; системные службы и настройки модели от этого не меняются.

Модель GGUF, llama.cpp и зависимости ОС поставляются отдельными штатными full/LLM-сборками. Публикация нового установочного релиза выполняется релизным процессом; успешная локальная сборка каталога сама по себе не обновляет ранее опубликованные assets.
