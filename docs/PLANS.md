# Планы

## Назначение

Контур хранит планы как проверяемые основания для будущих мероприятий и сроков. Источник истины — исходная версия документа и подтверждённые предметные записи; календарь, поиск и отчётные представления являются проекциями.

`plans` не заменяет `plan-fact`: план отвечает на вопрос «что запланировано и на каком основании», а `plan-fact` — «что выполнено и каким результатом подтверждено».

## Виды планов

- `department` — кафедра;
- `faculty` — факультет;
- `personal` — личный план сотрудника;
- `unit` — подразделение;
- `organization` — организация.

Период может быть календарным годом `2026`, учебным годом `2026/27` или, для импортированного документа, неопределённым до проверки оператором.

## Загрузка готового плана

```text
файл
→ immutable blob + document_version
→ извлечение текста и document_blocks
→ детерминированный plan extractor
→ plan + plan_items + evidence
→ FTS/facets + review_items
→ calendar_items(source_kind=plan_item)
```

Поддерживаемая структура таблицы определяется по заголовкам, а не по фиксированным номерам столбцов. Распознаются варианты заголовков для номера, мероприятия, даты/периода, контрольного срока, ответственного, результата и направления.

Если оператор не указывает вид плана и год, система пытается определить их из документа. Для учебного года месяцы с сентября по декабрь относятся к первому году, с января по август — ко второму.

Неоднозначность не блокирует документ. Пункт без даты, неопознанный ответственный или неизвестный год сохраняются и создают один вопрос в очереди проверки; остальные строки продолжают обрабатываться.

## Доказательства

Для табличного пункта сохраняются:

- таблица и строка;
- исходный текст строки;
- локаторы использованных ячеек;
- отдельные локаторы полей: название, номер, дата, срок, ответственный, результат и направление;
- уверенность детерминированного разбора.

Для текстового fallback сохраняется номер строки. Исходный файл никогда не переписывается.

## Календарь

Пункт плана может дать две проекции:

- событие по дате/периоду проведения;
- задачу по отдельному контрольному сроку.

Проекция хранит `source_kind = plan_item` и `source_id = <plan_item>`. Через пункт восстанавливаются план, период, исходная версия документа и доказательство. Повторный разбор той же версии плана не создаёт второй план и дубли календаря.

В интерфейсе календарная запись показывает происхождение: `План кафедры · 2026`, `План факультета · 2026/27`, `Личный план` и т. п. Из инспектора можно открыть план и исходный документ.

## Личные планы и права

Личный план имеет `owner_person_id`. При включённой авторизации:

- сотрудник видит собственный личный план и его календарные записи;
- руководитель видит свои планы и планы сотрудников своей иерархии;
- посторонний сотрудник не получает план через `/api/plans`, `/api/calendar`, `/api/tasks` или прямое открытие календарной записи;
- администратор имеет административный обзор.

Это предметная защита личного контура. Единая объектная ACL для всех документов и материалов развивается отдельно в issue #23.

## DOCX-шаблон формирования

Шаблон создаётся из неизменяемого DOCX-образца. Анализ автоматически определяет:

- текущий год или заполнитель года;
- таблицу мероприятий;
- строку заголовка;
- строку-образец;
- карту столбцов.

Перед сохранением оператор может исправить настройки. Каждая версия конфигурации шаблона сохраняется отдельно.

### Генерация

1. Оператор выбирает шаблон, вид плана и календарный/учебный год.
2. Заполняет строки в табличном редакторе.
3. Генератор открывает OOXML исходного DOCX.
4. Год заменяется в текстовых узлах.
5. Строка-образец клонируется для каждого пункта, что сохраняет её оформление.
6. Полученный DOCX сохраняется новым blob и новой версией документа.
7. Документ автоматически проходит штатный `process_plan_document`.
8. Результат снова получается из содержимого сформированного файла, а не из доверия к данным формы.

Таким образом, сформированный документ и импортированный документ имеют один и тот же последующий путь обработки.

## Идемпотентность

- импорт документа использует стандартную идемпотентность document intake;
- `plans` уникален по `workspace_id + source_document_version_id`;
- `plan_items` уникальны по `plan_id + source_row_key`;
- генерация шаблона имеет `request_key`, основанный на переданном ключе или SHA-256 нормализованной полезной нагрузки;
- календарная проекция использует существующий источник `plan_item` и не размножается при повторной обработке.

## Поиск

План и его пункты индексируются в общем FTS. Предметный список `/api/plans` дополнительно фильтруется по:

- тексту;
- виду плана;
- календарному/учебному году;
- направлению;
- ответственному;
- владельцу личного плана;
- состоянию.

Плановые сущности используют общий `entity_facets`, поэтому дальнейшее объединение с общим фасетным экраном не требует отдельной параллельной поисковой архитектуры.

## Проверки

Минимальный release gate контура:

- unit/integration: русский календарный год, учебный год и переход января на следующий год;
- структурная таблица и доказательства;
- точное сопоставление сотрудника;
- идемпотентная повторная обработка;
- DOCX ZIP/OOXML: замена года и размножение строки;
- Playwright desktop/mobile: DOCX-шаблон → анализ → формирование → worker → план → календарь → источник;
- auth Playwright: личный план и его календарь не видны постороннему сотруднику;
- общий backup/restore self-test после миграций.
