# Целевая эксплуатационная приёмка Astra Linux / Debian

Этот документ дополняет issue #27. Автоматический Ubuntu CI не закрывает целевую приёмку. Приёмка выполняется на реальной машине тем же автономным release-архивом, который прошёл CI.

## Что автоматизирует акт

`node scripts/target-acceptance.mjs capture` создаёт JSON-доказательство состояния установки без содержимого документов и без секретов конфигурации.

В акт входят:

- версия приложения и фактический `process.execPath`;
- Node version, platform, arch и доступные сведения glibc;
- `/etc/os-release`, `uname`, `ldd` embedded Node;
- system preflight;
- версии `pdftotext`, `pdftoppm`, Tesseract и LibreOffice;
- `PRAGMA quick_check` и текущая версия схемы;
- счётчики и логический SHA-256 устойчивых предметных таблиц;
- агрегированный digest предметной SQLite-модели;
- счётчики таблиц истории и транзитных таблиц отдельно от предметного снимка;
- полная проверка каждого `file_blobs`: существование, размер, SHA-256;
- агрегированный digest immutable blob-набора;
- состояние API/worker и ключевые systemd hardening properties;
- наличие, размер и SHA-256 последней проверенной backup-копии.

В акт не записываются SMTP password, Telegram token, пароли пользователей в открытом виде, cookie/session tokens, содержимое документов или полный env-файл. Хэши паролей могут входить только в логический digest таблицы аккаунтов и не выводятся как строки.

## Что считается устойчивым снимком

Для сравнения до/после restore хэшируются предметные таблицы документов, календаря, шаблонов, сотрудников, распоряжений и поручений, отчётности (включая связи периодических задач с отчётами и статус их проверки), plan/fact, науки, ACL, планов, аккаунтов и пользовательских настроек доставки.

Таблицы очереди, активных сессий и производных поисковых индексов не используются как критерий равенства. Исторические таблицы (`audit`, review, delivery history) могут пополниться при эксплуатации, но после восстановления их число строк не имеет права стать меньше эталонного.

`file_blobs.storage_path` намеренно не используется как межузловой критерий. Фактический файл проверяется по ожидаемому размеру и SHA-256; это позволяет восстановить систему на контрольный узел с тем же содержимым без ложного требования идентичного внутреннего пути.

## Подготовка эталонного снимка

После установки и загрузки контрольного реалистичного набора данных:

1. закончить все изменяющие операции оператора;
2. дождаться завершения обработки документов;
3. создать зашифрованную резервную копию штатной командой;
4. выполнить штатную проверку backup;
5. только после этого снять эталонный акт.

```bash
sudo /opt/kafedra-planner/current/runtime/node/bin/node \
  /opt/kafedra-planner/current/scripts/target-acceptance.mjs capture \
  --config /etc/kafedra-planner/kafedra-planner.env \
  --require-full \
  --output /root/kafedra-acceptance-before.json
```

`--require-full` делает блокирующими:

- отсутствие обязательных системных команд;
- отсутствие OCR (`pdftoppm` + Tesseract);
- отсутствие LibreOffice;
- отсутствие актуальной проверенной зашифрованной backup-копии;
- несоответствие версии схемы backup текущей БД;
- ошибки SQLite/blobs/systemd hardening.

Статус `pass`/`pass_with_warnings` не заменяет пользовательскую проверку реальных PDF/DOCX/XLSX/сканов; он подтверждает платформенную и информационную целостность.

## Контрольный сценарий #27

1. Проверить внешний SHA-256 автономного архива и embedded runtime.
2. Выполнить `preflight --strict --require-full` на целевой ОС.
3. Установить release штатным `install.sh`.
4. Создать первого администратора и выполнить вход.
5. Загрузить реалистичный набор: текстовый PDF, PDF-скан, DOCX, XLSX, распоряжение/приказ/указ, отчёт, научный материал и план.
6. Проверить OCR, LibreOffice preview, календарь, поиск, evidence, ACL и персональные права.
7. Дождаться завершения очереди изменяющих заданий.
8. Создать зашифрованную backup-копию и выполнить её штатный verify.
9. Снять `kafedra-acceptance-before.json`.
10. Зафиксировать начало восстановления для измерения RTO.
11. Разрушить тестовую установку согласно плану испытания либо восстановить копию на чистом контрольном узле.
12. Запустить API/worker, но до повторной операторской работы снять второй акт `kafedra-acceptance-after.json`.
13. Сравнить два акта машинной командой.
14. Пройти ключевые пользовательские сценарии после восстановления.
15. Отдельно искусственно сорвать обновление и подтвердить автоматический rollback.
16. После rollback снять ещё один акт и сравнить его с эталоном.
17. Зафиксировать RTO, замечания оператора и итоговые контрольные суммы.

## Снимок после восстановления

```bash
sudo /opt/kafedra-planner/current/runtime/node/bin/node \
  /opt/kafedra-planner/current/scripts/target-acceptance.mjs capture \
  --config /etc/kafedra-planner/kafedra-planner.env \
  --require-full \
  --output /root/kafedra-acceptance-after.json
```

## Машинное сравнение

```bash
/opt/kafedra-planner/current/runtime/node/bin/node \
  /opt/kafedra-planner/current/scripts/target-acceptance.mjs compare \
  /root/kafedra-acceptance-before.json \
  /root/kafedra-acceptance-after.json \
  --output /root/kafedra-acceptance-compare.json
```

Для успешного сравнения должны совпасть:

- версия приложения;
- версия схемы;
- счётчики устойчивых предметных таблиц;
- SHA-256 каждой устойчивой предметной таблицы и общий SQLite logical digest;
- количество и общий размер immutable blobs;
- агрегированный blob digest, включающий ожидаемый и фактический SHA-256/размер каждого файла.

Кроме того, исторические таблицы не должны терять строки относительно эталона.

Команда `compare` возвращает ненулевой код при любом критическом расхождении.

## Что считается отказом

Акт получает `fail`, если:

- отсутствует обязательная системная команда;
- в `--require-full` нет OCR или LibreOffice;
- в `--require-full` нет фактического файла последней verified+encrypted backup-копии;
- backup относится к другой версии схемы или приложения;
- `PRAGMA quick_check` не `ok`;
- отсутствует обязательная предметная таблица текущей схемы;
- отсутствует blob из `file_blobs`;
- размер или SHA-256 blob не совпадает;
- API/worker недоступны через systemd;
- ключевые параметры hardening systemd отличаются от ожидаемых.

`compare` считается неуспешным, если предметный digest, схема или immutable blobs отличаются либо история стала короче.

## Что остаётся ручным доказательством

Автоматизировать без потери смысла нельзя:

- визуальную корректность реального предпросмотра LibreOffice;
- качество OCR конкретных ведомственных сканов;
- понятность интерфейса оператору без инструкции;
- реальное время восстановления и организационный RTO;
- факт автоматического rollback при специально сорванном обновлении;
- совместимость embedded Node и системных библиотек конкретной редакции Astra за пределами фактически проверенной машины.

Именно поэтому #27 закрывается только после фактического испытания, а не после появления этого скрипта.
