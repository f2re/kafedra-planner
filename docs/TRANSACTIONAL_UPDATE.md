# Транзакционная установка и обновление

Штатная команда для чистой установки и для обновления существующей системы одна и та же:

```bash
sudo ./install-kafedra-planner.sh
```

Начиная с текущего release-контракта корневой `install.sh` является внешней транзакционной границей. Внутренний `install-core.sh` по-прежнему отвечает за additive-only установку недостающих пакетов ОС, staging релиза, backup, миграции, systemd, LLM и health-check. Внешний слой не дублирует эту логику: он гарантирует, что её можно либо завершить, либо вернуть прежнее рабочее состояние.

## Что происходит при обновлении

1. До остановки служб проверяются внешний архив, внутренний `manifest.sha256`, `release.json`, runtime/deployment contract и свободное место.
2. `flock` на `/run/lock/kafedra-planner-install.lock` запрещает два параллельных install/update процесса.
3. В `/var/lib/kafedra-planner-installer/active` сохраняется root-only journal: тип и цель `current`, точная копия конфигурации, systemd units, enabled/active state и факт существования БД.
4. API, worker и managed LLM останавливаются, после чего установщик до 30 секунд подтверждает, что они действительно inactive. До этого момента `current` и данные не переключаются.
5. Старая установка, где `/opt/kafedra-planner/current` является обычным каталогом, автоматически принимается как immutable `releases/legacy-*`. После этого дальнейшее переключение `current` выполняется только symlink-операцией.
6. Внутренний installer создаёт и проверяет `pre-update` backup, а внешний journal фиксирует путь точки отката до миграции/переключения.
7. После миграций и запуска обязательны version check, active API/worker и `/api/system/health`.
8. Только после этих проверок journal получает `phase=committed` и удаляется.

Повторный запуск того же bundle является штатным update: миграции и health-check повторяются, пользовательские данные, PIN, blobs и локальная конфигурация не пересоздаются.

## Автоматический откат

При ошибке core installer, post-update verification, неожиданной shell-ошибке, `SIGINT` или `SIGTERM` внешний слой:

- гарантированно останавливает новые службы;
- восстанавливает данные из проверенного `pre-update` backup, если БД существовала;
- возвращает точную конфигурацию до запуска update;
- возвращает прежний `current` — включая старый вариант с обычным каталогом;
- возвращает прежние systemd unit files и enabled state;
- запускает только те API/worker, которые были активны до update, и проверяет `/api/system/health`;
- сохраняет GGUF model cache отдельно от restore данных и возвращает его после восстановления.

Если процесс был убит `SIGKILL` или питание пропало, journal остаётся на диске. Следующий запуск сначала восстанавливает незавершённую транзакцию и только после успешного rollback начинает новое обновление. `phase=committed` и `phase=rolled-back` считаются финальными: после аварии между фиксацией финального состояния и удалением journal повторный запуск просто очищает journal и не делает ложный rollback.

Если сам rollback не прошёл проверку, установщик завершится кодом `90`, оставит journal на месте и не начнёт новую установку. Это намеренно fail-closed поведение: дальнейшее автоматическое изменение системы запрещено, пока не восстановлено доказуемое рабочее состояние.

## Диагностика

Основной root-only журнал:

```text
/var/log/kafedra-planner-install.log
```

Journal незавершённой или неудачно откатившейся транзакции:

```text
/var/lib/kafedra-planner-installer/active/
```

Точки отката приложения и данных остаются в:

```text
/var/backups/kafedra-planner/
```

Не удаляйте `active/` вручную при коде `90`: он содержит снимок `current/config/systemd`, необходимый для восстановления.

## Граница гарантии

Транзакционный слой гарантирует состояние самого Kafedra Planner: application release, SQLite/blobs, конфигурацию и systemd state. Пакетный менеджер ОС остаётся отдельной системной транзакцией: `install-core.sh` использует существующую политику `additive-only-v2`, запрещает upgrade/downgrade/remove и не запускает автоматический `apt --fix-broken`. Если `dpkg/apt` уже повреждены либо начали собственную неуспешную системную транзакцию, приложение не пытается «откатывать Debian/Astra» и сообщает отдельную диагностическую ошибку.
