# Пользовательские сценарии и UX-контракт

Статус: рабочие контуры версии `0.4.4`, схема SQLite `31`. Здесь описано фактически реализованное поведение; дальнейшее развитие находится в [`ROADMAP.md`](ROADMAP.md).

## Общие принципы

1. Система автоматически делает однозначное, человек исправляет исключения.
2. Исходный файл, SHA-256, `document_version`, machine result, locator и история не уничтожаются ручной правкой.
3. Ошибка одного файла, строки или необязательной интеграции не блокирует остальные данные.
4. Сохранённое значение → явный выбор → domain-derived контекст → safe personal default → static fallback.
5. ACL, PIN, выполнение, удаление/archive/restore, подтверждения и свободный деловой текст — `never-learn`.
6. Календарь, поиск и `План / факт` являются проекциями и ведут к рабочему источнику истины.
7. Безопасно обратимые действия выполняются сразу, без лишнего подтверждающего экрана.

Подробно: [`ADAPTIVE_UX.md`](ADAPTIVE_UX.md), [`SIMPLE_COMPLETION.md`](SIMPLE_COMPLETION.md), [`ARCHITECTURE.md`](ARCHITECTURE.md).

## 1. Вход и календарь

При первом открытии пользователь задаёт четырёхзначный PIN. В штатном локальном режиме отдельный логин и временный пароль не нужны.

Стартовый вид календаря выбирается явно: `Автоматически / Месяц / Неделя / Задачи`. Сохранённая настройка имеет приоритет над learned defaults.

`+` на конкретном дне сразу открывает короткую форму в контексте этого дня. Главным полем остаётся название; дата берётся как `domain-derived`, а редкие поля — категория, важность, напоминание, описание — находятся под одним раскрытием **Дополнительно**. Глобальное `+ Добавить` остаётся универсальным входом.

## 2. Календарь → план

Создание пункта плана из календаря сохраняет выбранную дату и не заставляет вводить её повторно.

- нет планов → пользователь создаёт план и автоматически продолжает исходный пункт;
- один план → сразу открывается форма пункта;
- несколько планов → выбор плана выполняется в том же продолжении, затем открывается существующая форма пункта.

Календарь не становится вторым редактором истины: сохраняется обычный `plan_item`, после чего проекция синхронизируется штатным доменным кодом.

## 3. Документы, OCR и повторная обработка

```text
загрузить
→ сохранить immutable source
→ извлечь текст/структуру
→ при необходимости OCR
→ создать рабочий объект
→ исправить только неоднозначности
```

Каждый файл сначала сохраняется как неизменяемая `document_version`. Upload UI различает реальный подтверждённый успех, обработку и ошибку по ответам сервера; смешанный batch не выдаётся за полностью успешный.

PDF OCR идёт постранично. Сохраняются абсолютный номер страницы, coverage, геометрия/locator и диагностический статус. Сбой одной страницы сохраняет хорошие страницы. Текстовая обложка не выключает OCR следующей сканированной страницы.

Действие повторной обработки создаёт новый `extraction_run` для той же immutable `document_version`; старый machine result не переписывается. Ручное рабочее значение сохраняет приоритет, а новое расхождение становится review-by-exception.

## 4. Планы, задачи и выполнение

Импортированный план сохраняет реальные исходные строки/ячейки и locators. Одну строку можно разложить на несколько обычных пунктов. Неизвестные колонки не выбрасываются.

Если ФИО точно совпало с единственным активным сотрудником, система создаёт связанную задачу. Неоднозначное имя не угадывается.

Для выполнения достаточно действия **Выполнено**. В одной предметной операции обновляются задача, пункт плана, календарь и `План / факт`. Файл, справка, скан или комментарий необязательны. **Вернуть в работу** сохраняет историю и снимает завершение связанных проекций.

Для периодической задачи используется тот же прямой предметный переход: `Выполнено / Вернуть в работу`. Необязательный отчёт или материал не определяет статус задачи.

## 5. Поиск

Результат поиска открывает точный рабочий объект, а не общий список: решение ведёт к заседанию, пункт — к плану, template extraction — к исходному документу, assignment/periodic task — к соответствующей рабочей карточке.

Основная карточка результата кликабельна целиком и доступна с клавиатуры. Ссылка на оригинал остаётся отдельным вторичным действием. После **К поиску** восстанавливаются запрос, фильтры, раскрытие редких фильтров, прокрутка и фокус.

## 6. Персональные подстановки

Пользователь может открыть **Подсказки**, выключить обучение, сбросить learned choices и закрепить безопасный уже встречавшийся default. Закрепление не разрешается для опасных состояний и `never-learn` действий.

Отключение обучения прекращает запись/использование частотных подсказок, но не отменяет явные/сохранённые/domain-derived значения и безопасные pins. Программная подстановка не считается пользовательским выбором.

## 7. Заседания и протоколы

Новое заседание можно начать с даты и номера протокола без предварительной настройки выпуска. Повестка открывается сразу. Полные настройки и шаблоны, если они есть, по-прежнему используются при формировании итогового документа.

Для накопленных протоколов:

```text
Заседания → выбрать год
→ Загрузить протоколы
→ выбрать несколько DOCX/ODT/PDF/TXT
→ сохранить каждый immutable source
→ независимо обработать
→ открыть только исключения
```

Сводка различает `Готово / Нужно проверить / Ошибка / Обрабатывается` и восстанавливается из устойчивых данных. Один плохой документ не откатывает соседние.

Базовый `department_protocol` parser работает автономно. Для стабильного локального формата можно использовать дополнительный детерминированный профиль на базе document template: он сохраняет profile-поля с locator текущей версии, не перезаписывает ручное рабочее значение и локализует ошибку одного профиля. Реальная двухдокументная приёмка такого профиля остаётся в issue #326.

Подробно: [`MEETINGS.md`](MEETINGS.md), [`PROTOCOL_PROFILES.md`](PROTOCOL_PROFILES.md).

## 8. Оформлятор

Интеграция находится в **Настройки → Структура кафедры → Импорт из Оформлятора** и остаётся необязательной.

```text
вставить один адрес
→ Подключить
→ при необходимости ввести 4-значный код
→ выбрать пространство/группу/поля
→ проверить краткий preview
→ Импортировать сотрудников
```

Planner различает DNS, refused port, timeout, TLS, wrong service, not-ready, access и incompatible protocol. Код используется только в текущем запросе и не сохраняется. Ошибка одного удалённого профиля не отменяет успешно импортированные записи. При недоступности Оформлятора локальный справочник продолжает работать.

Подробно: [`DOCOMATOR_PEOPLE_IMPORT.md`](DOCOMATOR_PEOPLE_IMPORT.md).

## 9. Учебный процесс

XLSX/ODS/CSV проходят обычный document intake. Группа, учебный год и семестр берутся из точной ячейки либо вводятся вручную; вымышленный locator не создаётся. Одна ошибочная строка не отменяет остальные оценки. Для пары `группа + период` текущей является последняя успешная ведомость, а superseded/failed/archived остаются в истории.

## 10. Архивирование

Архивирование документа или плана меняет lifecycle, а не уничтожает данные. `document_version`, blob, evidence, источники пунктов, calendar origin, задачи, материалы и завершённые факты сохраняются. Restore обратим. Необязательный преемник является навигационной связью, а не перепривязкой истории.

## 11. Установка и обновление

Release bundle можно держать в обычной читаемой пользовательской папке. Wrapper сам получает root-права, проверяет внешний SHA-256 и внутренний manifest, извлекает bundle в приватный root staging и не делает `chown` исходного каталога.

Full bundle содержит managed Node.js/CPython и локальное замыкание document capabilities. Установщик запрашивает только отсутствующие пакеты, не фиксирует target `package=version`, не делает upgrade/downgrade/remove и автоматически не запускает `apt --fix-broken`.

До переключения `/opt/kafedra-planner/current` обязательно проходят strict preflight и реальный OCR self-test для Tesseract `rus+eng`/Poppler; также проверяется LibreOffice. Если полный document runtime не работает, новый release не активируется. После переключения выполняются migrations, health/doctor и rollback при ошибке.

## 12. Release

Pull request доказывает полный project CI один раз. После squash merge запускается только короткий post-merge smoke.

Единственный version-neutral workflow `Release` стартует только от exact текущего `main` — вручную или через служебный `release-run`, указывающий на тот же SHA. Он один раз выполняет project/unit/smoke/backup и critical browser, собирает один full offline artifact и проверяет именно его через checksum, Debian 12 systemd clean install, repeated update и forced rollback. Project Control и публикуемые assets создаются из уже проверенного archive без пересборки.

Release не ждёт другие Actions, не вызывает `gh workflow run` и не повторяет доказанные suites отдельным orchestration-слоем. CI дополняет, но не заменяет реальную целевую Astra Linux/Debian-приёмку.
