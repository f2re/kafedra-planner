# Пользовательские сценарии и UX-контракт

Статус: рабочие контуры версии `0.3.4`, схема SQLite `30`. Здесь описывается только фактически реализованное поведение; планы дальнейшего развития остаются в [`ROADMAP.md`](ROADMAP.md).

## Общие принципы

1. **Сразу к работе.** После входа пользователь попадает в календарь.
2. **Система сокращает бюрократию.** Не добавляются обязательные отчёты, подтверждения или согласования, если результат можно безопасно применить сразу и оставить редактируемым.
3. **Стабильная геометрия.** Частота использования не переставляет кнопки, вкладки и основные секции.
4. **Явная настройка сильнее обучения.** Постоянная настройка стартового режима календаря имеет приоритет над learned UX.
5. **Предметные данные сильнее статистики.** Сохранённая дата, выбранный день, вычисленный период, найденный руководитель и другие domain-derived значения не заменяются learned default.
6. **Только явный выбор человека.** Программная подстановка и synthetic DOM events не обучают preference-layer.
7. **Безопасная адаптация.** Контролы классифицируются как `safe-default / rank-only / domain-derived / never-learn`.
8. **Не блокировать основной сценарий.** Ошибка preference-layer, внешней доставки, интеграции, материала или LLM не мешает предметному сохранению и выполнению.
9. **Минимум модальных окон.** Формы открываются в листах/инспекторе и сохраняют введённые значения при временной ошибке.
10. **Происхождение видно рядом с результатом.** Документ, исходная строка плана, календарная задача, внешний сотрудник и связанный материал ведут к источнику/evidence.
11. **Desktop/mobile — один предметный сценарий.** На мобильном меняется компоновка, а не смысл действий.
12. **Удаление заменено обратимым lifecycle.** Исходный документ или план архивируется, но не уничтожается и не перепривязывает историю к другому источнику.

Подробный preference-контракт: [`ADAPTIVE_UX.md`](ADAPTIVE_UX.md). Простой контур выполнения: [`SIMPLE_COMPLETION.md`](SIMPLE_COMPLETION.md).

## 1. Старт календаря

Пользователь может выбрать постоянную настройку:

```text
Автоматически / Месяц / Неделя / Задачи
```

- `Месяц`, `Неделя`, `Задачи` открываются всегда, пока пользователь не изменит настройку;
- `Автоматически` разрешает безопасный learned default/fallback;
- обычное переключение текущего вида не переписывает постоянную настройку;
- порядок кнопок остаётся фиксированным;
- настройка account-scoped при авторизации и имеет безопасный local fallback без auth.

Подробно: [`CALENDAR_START_MODE.md`](CALENDAR_START_MODE.md).

## 2. Создание события или задачи

1. Пользователь нажимает `Создать` либо `+` внутри конкретного дня.
2. Форма открывается в контексте календаря.
3. Конкретный выбранный день имеет приоритет над learned relative-date default.
4. Безопасные тип, категория, важность и напоминание могут предлагаться как personal default только для нового объекта.
5. После успешного сохранения запись появляется без перезагрузки.
6. Задачу можно завершить одним действием и при необходимости вернуть в работу.

Редактирование существующей записи всегда показывает её сохранённые значения, а не статистические defaults.

## 3. Уведомления

- внутренний центр уведомлений работает без внешних сервисов;
- уведомление объясняет объект и действительно требуемое действие;
- выполненные и отменённые обязательства не продолжают создавать повторные напоминания;
- прикреплённый материал не создаёт уведомление о необходимости подтверждения;
- read/hide сохраняются серверно;
- SMTP/Telegram являются дополнительными каналами и не заменяют внутреннее уведомление;
- повторный worker run не создаёт дубликат одного notification key.

Подробно: [`NOTIFICATION_DELIVERY.md`](NOTIFICATION_DELIVERY.md).

## 4. Документы: от загрузки до рабочего объекта

В начале раздела показаны три понятных назначения:

- **Основание** — приказ, распоряжение или указ;
- **План** — документ с мероприятиями, сроками и ответственными;
- **Материал** — справка, подтверждение, скан или другой необязательный файл.

Рабочий сценарий:

1. Пользователь загружает один или несколько файлов.
2. Каждый файл сохраняется до фоновой обработки как immutable `document_version`.
3. Ошибка одного файла не останавливает остальные.
4. Worker извлекает text/structure, при необходимости локально использует OCR/LibreOffice.
5. Список показывает русские названия вида и состояния; внутренние `unknown`, `faculty_plan` и технические коды не выдаются за операторские термины.
6. Поиск и переключатель `В работе / Архив` сокращают список.
7. В инспекторе доступны исходник/preview, извлечённые поля, evidence, переименование, уточнение вида, архивирование и восстановление.
8. Переименование и вид меняют только метаданные; blob, версия, исходное имя, SHA-256 и доказательства остаются прежними.

Подробно: [`STRUCTURED_DOCUMENTS.md`](STRUCTURED_DOCUMENTS.md), [`OCR_AND_PREVIEW.md`](OCR_AND_PREVIEW.md).

## 5. Архивирование и безопасная замена документа

1. Пользователь нажимает `В архив`.
2. До подтверждения система показывает влияние: версии, планы и пункты, календарные записи, задачи, распоряжения, заседания, шаблоны и сопроводительные связи.
3. Пользователь может указать причину и необязательный активный документ-преемник.
4. После подтверждения исходник остаётся доступным в архиве, а рабочий список по умолчанию его скрывает.
5. В архиве видна навигация к преемнику и действие `Восстановить`.

Связь замены не переписывает `document_version`, `plan.source_document_version_id`, `plan_item`, задачи, материалы и evidence. Self-reference, другой workspace, архивный преемник и цикл блокируются. Архивирование, выбор преемника и восстановление — `never-learn`.

Подробно: [`DOCUMENT_PLAN_LIFECYCLE.md`](DOCUMENT_PLAN_LIFECYCLE.md).

## 6. Шаблон документа

1. Оператор выбирает исходный документ.
2. Размечает поддержанные поля и структурные якоря.
3. Проверяет извлечение до сохранения.
4. Неоднозначность показывается как исправимый вопрос, а не техническая ошибка.
5. Исходный документ не изменяется.
6. Черновик мастера может восстанавливаться без создания предметного результата.

Безопасные repeatable-настройки поля могут использовать preference-layer; имя шаблона и свободный деловой текст не обучаются.

## 7. Сотрудники: импорт из Оформлятора

Интеграция находится в **Настройки → Структура кафедры → Импорт из Оформлятора** и не является обязательной для локальной работы.

1. Администратор выбирает HTTP/HTTPS, вводит адрес и порт; стандартный порт — `8080`.
2. При необходимости вводит четырёхзначный код доступа только для текущей операции. Значение не сохраняется и относится к `never-learn`.
3. `Проверить соединение` последовательно различает `/healthz`, `/readyz`, требование кода и доступность прикладных данных.
4. После успешной проверки выбираются пространство и конкретная группа либо все сотрудники пространства.
5. До импорта показываются количество и короткий preview ФИО; неактивные сотрудники включаются только явным флагом.
6. Импорт сопоставляет запись по сохранённому remote employee id, а при первой синхронизации может переиспользовать существующего человека по нормализованному ФИО.
7. Повторный импорт обновляет ту же локальную запись и не создаёт дубль.
8. Изменение ФИО или статуса не удаляет локальные планы, задачи, материалы, назначения и историю.
9. Недоступность или несовместимость Оформлятора не блокирует ручную работу со справочником и остальные разделы.

Host/port и выбранный источник являются явными server settings; статистика использования их не изменяет. Пространство и группа — `rank-only`, но нейтральный выбор не подменяется молча. Код доступа и включение неактивных записей — `never-learn`.

Подробно: [`DOCOMATOR_PEOPLE_IMPORT.md`](DOCOMATOR_PEOPLE_IMPORT.md).

## 8. Годовой план

План можно импортировать либо создать вручную.

### Импорт и разбор строк

```text
immutable document_version
        ↓
plan_source_rows + исходные ячейки/локаторы
        ↓ 1:N
plan_items
        ↓
календарь и, при необходимости, задачи
```

1. Система сохраняет таблицы, строки и реальные номера ячеек без сдвига из-за пустых колонок.
2. Для каждой строки предлагает мероприятие, сроки, направление, ответственного и ожидаемый результат.
3. Неизвестные колонки не выбрасываются и могут быть оставлены в комментарии.
4. Однозначные строки можно принять быстро; первыми показываются строки, требующие внимания.
5. Одну исходную строку можно разделить на несколько обычных задач.
6. Для каждой задачи выбираются собственные даты, режим исполнения, несколько исполнителей и необязательный контролирующий.
7. Если извлечённое ФИО точно совпадает с единственным активным сотрудником, система создаёт одну связанную задачу и показывает состояние `Назначен`.
8. Контролирующий выводится из актуального основного назначения сотрудника на дату задачи; отсутствие руководителя не блокирует задачу и её выполнение.
9. При двух совпадениях, сокращённом или отсутствующем ФИО система ничего не угадывает: сохраняет исходное значение и предлагает оператору исправить назначение.
10. Повторное сохранение идемпотентно; уже существующая, отредактированная или завершённая задача не удаляется и не переписывается молча.
11. Проблемная строка не блокирует обработку остальных.
12. После загрузки интерфейс выбирает план, созданный именно из полученного `documentId`, а не случайную ранее активную карточку.

Автоматическое точное сопоставление и контролирующий из оргструктуры относятся к `domain-derived`; завершение, архив и ручное переназначение относятся к `never-learn`.

Подробно: [`PLAN_SOURCE_ROWS.md`](PLAN_SOURCE_ROWS.md), [`AUTOMATIC_ASSIGNMENTS.md`](AUTOMATIC_ASSIGNMENTS.md).

### Ручной план

1. Пользователь создаёт календарный или учебный план.
2. Добавляет пункт из карточки либо через `В план` в календаре.
3. Выбирает режим:
   - `track` — контрольная точка;
   - `assigned` — задача выбранным исполнителям;
   - `open` — открытая задача для самостоятельного принятия.
4. Один `plan_item` имеет не более одной связанной задачи.
5. Прогресс, комментарии и необязательные материалы используют общий рабочий контур.
6. `Выполнено` сразу синхронизирует план, календарь и `План / факт`.

Подробно: [`PLANS.md`](PLANS.md), [`MANUAL_PLANS.md`](MANUAL_PLANS.md).

## 9. Lifecycle плана

В списке по умолчанию показываются планы `В работе`; архив открывается явным фильтром.

1. В карточке плана доступны переименование, добавление мероприятия, формирование DOCX и архивирование.
2. Перед архивированием видны число пунктов, календарных проекций, задач, активных обязательств, сопроводительных документов и вопросов заседаний.
3. Можно выбрать активный план-преемник.
4. Старый план и его пункты остаются на месте, календарный `origin_id` и связанные задачи не меняются.
5. Архивный план можно восстановить; навигационная связь с преемником при восстановлении снимается.

Перенос незавершённых обязательств между пунктами разных планов не выполняется автоматически. Такой перенос потребует отдельного явного сопоставления. Lifecycle-действия относятся к `never-learn`.

Подробно: [`DOCUMENT_PLAN_LIFECYCLE.md`](DOCUMENT_PLAN_LIFECYCLE.md).

## 10. Задача → выполнено → План / факт

1. Задача возникает из основания либо пункта плана.
2. Сотрудник может сохранять прогресс и комментарии.
3. Для завершения достаточно действия `Выполнено`.
4. Система сразу обновляет задачу, связанный пункт плана, календарь и `План / факт`.
5. Руководитель не обязан подтверждать или возвращать результат.
6. PDF, DOCX, справка, скан или иной материал можно приложить до или после выполнения; это необязательно и не меняет статус.
7. Автоматика может предложить связь документа с задачей, но не закрывает задачу и не создаёт очередь согласования.
8. История, evidence и предыдущие материалы сохраняются.

Подробно: [`SIMPLE_COMPLETION.md`](SIMPLE_COMPLETION.md), [`WORKFLOW_DOCUMENTS.md`](WORKFLOW_DOCUMENTS.md), [`PLAN_FACT.md`](PLAN_FACT.md).

## 11. Заседание кафедры

1. Секретарь создаёт заседание и указывает номер и дату.
2. Повестка формируется вручную, из пункта плана или задачи.
3. Вопросы имеют стабильную нумерацию.
4. Для каждого вопроса заполняются фактические `Слушали / Обсудили / Решили`.
5. Полный протокол либо выписка по выбранным вопросам формируются в DOCX.
6. Повтор неизменённой генерации не создаёт второй документ.
7. Пункт плана получает обратную ссылку на заседание, протокол и вопрос.
8. Библиотека шаблонов хранит версии, основной шаблон, тестовое заполнение, архив и точную историческую версию генерации.

Подробно: [`MEETINGS.md`](MEETINGS.md), [`MEETING_TEMPLATES.md`](MEETING_TEMPLATES.md).

## 12. «План / факт»

- руководитель или сотрудник видит только разрешённую сервером выборку;
- плановое и фактическое значения раскрываются до источника;
- задача может быть выполнена без документа;
- необязательный материал может дать дополнительные фактические показатели;
- ручная корректировка требует причины и не уничтожает machine value;
- сохранённые views не расширяют ACL;
- CSV/JSON отражают текущую серверную выборку;
- риск срока вычисляется детерминированно.

Подробно: [`PLAN_FACT.md`](PLAN_FACT.md), [`PLAN_FACT_OPERATIONS.md`](PLAN_FACT_OPERATIONS.md).

## 13. Инспектор и восстановимость

- просмотр объекта не уводит пользователя из основного контекста;
- desktop использует боковой инспектор, mobile — нижний лист;
- Esc или закрытие возвращает фокус;
- обратимые действия предлагают простой return path;
- формы не очищаются при временной ошибке;
- успешная загрузка файла не повторяется только потому, что последующая связь временно упала;
- impact и последствия destructive-like действий формулируются предметно, а не абстрактным «Вы уверены?».

## 14. Обучаемый UX без скрытых решений

Примеры допустимого поведения:

- в `Автоматически` часто выбранная `Неделя` может стать стартовым видом;
- частая категория новой задачи может стать safe default;
- частый вариант фильтра может подняться в списке, но фильтр остаётся нейтральным;
- конкретный день календаря всегда сильнее learned date offset;
- найденный по структуре руководитель сильнее статистики;
- пароль, PIN внешней системы, токен, host, поиск, свободный текст, роль, ACL, выполнение, возврат в работу, archive/restore/replacement никогда не обучаются.

Приоритет:

```text
сохранённое значение / явный предметный контекст
→ явный выбор текущего действия
→ domain-derived значение
→ безопасный personal default
→ статический fallback
```

## 15. Release gate UX

Browser CI проверяет фактические package scripts:

```bash
npm run test:browser:plans
npm run test:browser:core
npm run test:browser:reports-science
npm run test:browser:plan-fact
npm run test:browser:auth
npm run test:browser:release
npm run test:browser:acl
```

`test:browser:plans` включает desktop/mobile сценарии исходных строк, нескольких задач и исполнителей, прямого завершения, необязательных материалов, документа и плана в архиве, выбора преемника и восстановления. Отдельные E2E проверяют точную цепочку `upload documentId → source planId → сотрудник → задача` и полный импорт Оформлятора. Browser CI дополняет, но не заменяет full-offline/systemd и целевую Astra-приёмку.
