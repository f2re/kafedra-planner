# Пользовательские сценарии и UX-контракт

Статус: рабочие контуры версии `0.4.2`, схема SQLite `31`. Здесь описывается только фактически реализованное поведение; дальнейшие этапы находятся в [`ROADMAP.md`](ROADMAP.md).

## Общие принципы

1. После входа пользователь сразу попадает к рабочему объекту, обычно в календарь.
2. Система автоматически выполняет однозначное и оставляет человеку только исключения.
3. Исходный файл, версия, SHA-256, evidence и история не уничтожаются ручной правкой.
4. Ошибка одного документа, строки, внешнего сервиса или preference-layer не блокирует остальные данные.
5. Отчётный файл и подтверждение руководителем не являются обязательными условиями выполнения обычной задачи.
6. Геометрия интерфейса не меняется от статистики использования.
7. Сохранённое предметное значение и явный текущий выбор сильнее learned default.
8. Desktop и mobile меняют компоновку, но не смысл действий.
9. Архивирование обратимо и не перепривязывает исторические факты к преемнику.
10. Техническая ошибка преобразуется в понятное оператору состояние и действие.

Подробно: [`ADAPTIVE_UX.md`](ADAPTIVE_UX.md), [`SIMPLE_COMPLETION.md`](SIMPLE_COMPLETION.md), [`ARCHITECTURE.md`](ARCHITECTURE.md).

## 1. Вход и старт календаря

При первом открытии пользователь задаёт четырёхзначный PIN. В штатном локальном режиме отдельный логин, регистрация и временный пароль не нужны.

Стартовый режим календаря выбирается явно:

```text
Автоматически / Месяц / Неделя / Задачи
```

Сохранённая настройка имеет приоритет. Обычное переключение текущего вида не переписывает её. Конкретно выбранный день календаря всегда сильнее learned date offset.

## 2. Создание события или задачи

1. Пользователь нажимает `Создать` либо `+` у конкретного дня.
2. Форма открывается в текущем календарном контексте.
3. Безопасные значения нового объекта могут предлагаться как default.
4. После успешного сохранения запись появляется без перезагрузки.
5. Задачу можно завершить одним действием и вернуть в работу.

Редактирование существующего объекта всегда показывает его сохранённые значения, а не статистические defaults.

## 3. Документы: от загрузки до рабочего объекта

1. Пользователь загружает один или несколько файлов.
2. Каждый файл сначала сохраняется как неизменяемая `document_version`.
3. Ошибка одного файла не останавливает остальные.
4. Worker извлекает текст и структуру, при необходимости локально использует OCR или LibreOffice.
5. Однозначные данные применяются с источником и locator.
6. Неоднозначности попадают в проверку исключений, но рабочий объект уже доступен.
7. В инспекторе видны исходник/preview, машинное значение, ручная правка, evidence и история.
8. Переименование, уточнение вида, архив и восстановление не изменяют blob и SHA-256.

## 4. Планы и исходные строки

```text
immutable document_version
        ↓
plan_source_rows + ячейки/локаторы
        ↓ 1:N
plan_items
        ↓
календарь и при необходимости задачи
```

Реальные номера колонок сохраняются, даже если часть ячеек пуста. Неизвестные колонки не выбрасываются. Одну строку можно разложить на несколько задач с собственными сроками, режимом и исполнителями.

Если ответственное ФИО точно совпало с единственным активным сотрудником, создаётся одна связанная задача. При двух совпадениях, сокращённом или отсутствующем ФИО система ничего не угадывает. Повторный materialize идемпотентен и не удаляет отредактированную или выполненную задачу.

## 5. Задача → Выполнено → План / факт

1. Задача возникает из распоряжения или пункта плана.
2. Сотрудник сохраняет прогресс и комментарии.
3. Для завершения достаточно `Выполнено`.
4. В одной предметной операции обновляются задача, пункт плана, календарь и `План / факт`.
5. PDF, DOCX, скан, справку или комментарий можно приложить до или после выполнения, но это необязательно.
6. Автоматическое сопоставление материала является предложением связи и не закрывает задачу.
7. `Вернуть в работу` сохраняет историю и снимает завершение связанных проекций.

## 6. Архивирование документа или плана

Перед архивированием система показывает impact: версии, пункты, календарные записи, задачи, заседания, шаблоны и сопроводительные связи. Можно указать причину и необязательный активный преемник.

Архивирование меняет только lifecycle исходного объекта. Оно не изменяет `document_version`, источник пункта плана, calendar origin, задачи, материалы и завершённые факты. В архиве доступны переход к преемнику и `Восстановить`.

## 7. Сотрудники: прямое подключение Оформлятора

Интеграция находится в **Настройки → Структура кафедры → Импорт из Оформлятора** и остаётся необязательной.

Основной путь:

```text
вставить адрес Оформлятора
→ Подключить
→ выбрать пространство и группу
→ выбрать переносимые поля
→ увидеть количество и ФИО
→ Импортировать сотрудников
```

1. Администратор вставляет один адрес, например `http://192.168.1.50:8080`, `https://docomator.local` или URL с известным окончанием `/api/v1`, `/healthz`, `/readyz`, `/api/v1/system/*`.
2. Протокол, порт и версия API не разделяются на дополнительные controls. Bare hostname/IP получает совместимый default `http:8080`; полный URL использует свой protocol default port.
3. Credentials, query, fragment, неподдерживаемая схема и посторонний path отклоняются до сетевого обращения.
4. Нажатие `Подключить` проверяет `/healthz`, `/readyz` и прикладные данные. Текущий `status: ok` и legacy `ready` поддерживаются одинаково.
5. При необходимости вводится четырёхзначный код Оформлятора. Код используется только в текущем запросе, не сохраняется и не восстанавливается в форме.
6. При единственном пространстве оно выбирается автоматически; группа по умолчанию — все сотрудники пространства.
7. ФИО переносится всегда. E-mail, должность и дополнительные свойства выбираются явно; mapping сохраняется до import request.
8. До импорта показываются количество и короткий escaped preview ФИО.
9. Синхронизация использует remote employee id; первая загрузка может сопоставить существующего человека по нормализованному ФИО.
10. Повторный импорт обновляет ту же запись и не создаёт дубль.
11. Ошибка отдельного удалённого профиля учитывается как `skipped`, а успешно обработанные записи сохраняются. Итог показывает total/created/updated/matched/skipped.
12. Изменение ФИО или статуса не удаляет локальные планы, задачи, материалы, назначения и историю.
13. DNS, refused port, timeout, TLS, wrong service, not-ready, denied code и incompatible protocol имеют отдельные сообщения. При ошибке скрывается только устаревший remote preview; локальный справочник остаётся доступен.

Запрос выполняет сервер Planner, поэтому имя Оформлятора должно разрешаться именно на этой машине. При отсутствии локального DNS можно вставить IP-адрес.

Классификация controls:

- адрес, код, подключение и импорт — `never-learn`;
- пространство и группа — `domain-derived` или явный текущий выбор;
- перенос свойств — предметная настройка, не изменяемая статистикой;
- программная подстановка единственного пространства не считается обучающим выбором.

На mobile сохраняется тот же порядок полей и действий; меняется только число колонок. Анимация не используется, `prefers-reduced-motion` не меняет поведение.

Подробно: [`DOCOMATOR_PEOPLE_IMPORT.md`](DOCOMATOR_PEOPLE_IMPORT.md).

## 8. Заседание кафедры

1. Секретарь создаёт заседание с номером и датой.
2. Повестка формируется вручную, из пункта плана или задачи.
3. Для каждого вопроса заполняются фактические `Слушали / Обсудили / Решили`.
4. Формируется полный протокол или выписка по выбранным вопросам.
5. Генерация использует точную версию DOCX-шаблона и регистрирует результат как обычный документ.
6. Повтор неизменённого запроса не создаёт второй файл.

## 9. Учебный процесс и успеваемость

Оператор загружает XLSX, ODS или CSV. Система предлагает лист, заголовки, колонку ФИО, дисциплины, группу, учебный год и семестр. Метаполе берётся из точной ячейки либо вводится вручную; фиктивный locator не создаётся.

Одна ошибочная строка или неизвестная оценка не отменяет остальные данные. Для пары `группа + период` текущей является последняя успешная ведомость, а superseded/failed/archived остаются в истории. Сводка и экспорт раскрываются до студента, версии документа, листа и ячейки.

## 10. Обновление установленного сайта

Release bundle можно держать в любой читаемой пользовательской папке. Wrapper сам получает root-права, проверяет checksum и manifest, извлекает содержимое в приватный root staging и не выполняет `chown` исходного каталога.

После backup и переключения release installer сравнивает обязательные UI-файлы активного `/opt/kafedra-planner/current` с выбранным bundle. Несовпадение вызывает rollback. HTML, JavaScript и CSS выдаются с `Cache-Control: no-store`, поэтому старый нефингерпринтованный интерфейс не должен сохраняться после успешного обновления.

Установленный код остаётся root-owned и non-writable для service user; данные остаются service-owned. Это разделение защищает код от изменения процессом приложения и не требует делать root-владельцем загрузочную папку пользователя.

## 11. Перезапуск и диагностика

```bash
sudo systemctl restart kafedra-planner-api.service kafedra-planner-worker.service
sudo systemctl status --no-pager -l kafedra-planner-api.service kafedra-planner-worker.service
sudo journalctl -u kafedra-planner-api.service -u kafedra-planner-worker.service -n 100 --no-pager
```

LLM-служба перезапускается отдельно только при её использовании.

## 12. Release gate UX

Browser CI проверяет desktop и mobile, direct Docomator URL, current/legacy readiness, access code, field mapping, preview, partial success, repeated import, classified errors, reduced motion, active UI verification, plans, meetings, academic performance, PIN/accounts and ACL.

Browser CI дополняет, но не заменяет full-offline/systemd и целевую Astra-приёмку.
