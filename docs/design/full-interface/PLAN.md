# Полный план исправления интерфейса Кафедра-планера

Дата: 5 октября 2026 года. Задача: #360. Исходная версия: 0.4.7, commit `688ffea1c6355980541da5ceb2b2e01f30116d76`.

Это план работы над существующим приложением, а не отчёт о завершённом редизайне. В текущем изменении обновляются инструкции дизайнеров, реестр и способы проверки полноты. Прикладной интерфейс, данные, схема, права и установщик этим планом не изменяются.

## 1. Как читать полный план

План состоит не только из этой записки:

- [FLOWS.md](FLOWS.md) — предметные сценарии, ветви, переходы между разделами и варианты повторно используемых окон.
- [ACCEPTANCE.md](ACCEPTANCE.md) — конкретные задания и критерии для каждой кнопки, поля, формы, окна, экрана и обработчика.
- `buttons-D1.tsv` … `buttons-D7.tsv` — отдельная строка для каждого найденного места создания кнопки: идентификатор, источник, функция/контекст, подпись, критерий, статус. Владелец определяется номером зоны файла.
- `windows.tsv`, `screens.tsv`, `forms.tsv` — отдельные исходные места создания окон, экранов и форм. Один контейнер окна с несколькими формами не считается одним пользовательским сценарием.
- `source-index.json` — пофайловая контрольная ведомость всех обнаруженных элементов и проверяемых вызовов, включая поля, опции, нестандартные интерактивные узлы и программный DOM.
- `tools/ui-audit/` — воспроизводимый сборщик развёрнутого `inventory.json` и ведомостей. Исходный индекс не заменяет проверку в браузере.
- [Договорённости дизайнеров](../../../codex/agents/design-team.md) и [Designer](../../../.agent/skills/designer/SKILL.md) — правила распределения и приёмки работ.

Задание на элемент равно: **его индивидуальная запись + контекст/исходник + владелец зоны + соответствующий сценарий FLOWS + полный контракт ACCEPTANCE**. Общий контракт наследуется каждым элементом, но доказательство результата указывается по конкретным идентификаторам. Общий пункт «проверить раздел» не закрывает ни одну строку.

## 3. Граница доказательств

Уже сделано: чтение действующих контрактов, анализ точек входа и исходных конструкций, поэлементная индексация, обновление маршрутизации Designer и согласование локальных ролей.

Не утверждается: что каждая кнопка нажата в браузере; что все динамические формы уже раскрыты на всех данных; что все действия выполняются правильно; что тесты из репозитория были выполнены только потому, что они существуют; что реальная Astra Linux и реальные документы пользователя прошли приёмку.

Статические кандидаты, скрытые ветви, динамические значения, составные селекторы и неизвестные связи обработчиков — обязательные задания этапа R0, а не молчаливые исключения. До их разрешения нельзя выдать окончательный PASS всему интерфейсу. Функции открытия окон могут использовать один контейнер для нескольких разных форм; проверяются все варианты, а не только наличие role=dialog.

## 4. Выводы анализа и порядок важности

### Уже устранённое противоречие инструкций

В прежнем `kafedra-design` требовалась формальная передача каждого GRACE-изменения `public/**` специалисту по анимации, хотя AGENTS и CODEX_AGENTS выбирают роли по фактическому риску. Designer и локальные design/motion/audit теперь согласованы: анимация только по необходимости, статическая правка не требует церемонии всех ролей, полный аудит требует полного охвата.

### Подтверждённые исходниками особенности, требующие работы

1. **Парольные сценарии через системные диалоги.** `auth-next.js:267,271,281` и `admin-next.js:264` используют prompt/alert. Задание D7: спроектировать нормальную краткую форму с маскированными полями, валидацией, понятной отменой и безопасным временем жизни введённых значений. Сначала проверить обе действующие модели входа; не отменять PIN и не менять backend авторизации под видом оформления.
2. **Несколько способов окон и подтверждений.** Собственные sheet/modal, нативные dialog, инспекторы и confirm встречаются в разных модулях. D1 определяет общий контракт поведения, затем каждая из 27 исходных оконных конструкций и каждая из 64 форм проходит отдельную приёмку. Различие механизмов само по себе ещё не доказывает ошибку фокуса.
3. **Сложная сборка интерфейса.** Части добавляются сервером, импортами, фабриками и усилителями существующего DOM. Нельзя исправлять только исходную разметку, игнорировать повторное открытие, изменение роли, позднюю загрузку и повторный запуск усилителя. D1/D7 проверяют порядок подключения и единичность обработчиков.
4. **Нативные подтверждения имеют разные предметные последствия.** Перенос даты из документа (`ux-base.js:383`), удаление вопроса (`meetings-actions.js:126`), архив протокола (`protocol-import-lifecycle.js:55`) и завершение сессий (`admin-next.js:310`) нельзя заменить одной безликой формой. Проверяются понятное название объекта, последствия, отмена и возможность восстановления. У обратимой рутины не должно появляться лишних подтверждений.
5. **Две версии lifecycle и отдельный неподключённый origin-модуль.** Проверить `lifecycle-next.js` против действующего `lifecycle-safe.js`, а также `plan-fact-origin.js`. Сначала установить реальную связь с входами/тестами, затем объединять или удалять. Не вводить третью реализацию.

### Риски, которые ещё требуется подтвердить поведением

- В ряде обработчиков есть `.catch(() => {})`, в частности у вызовов План / факт, просмотра научных объектов и вспомогательных обновлений. Нужно проверить, показывает ли ошибку вложенная функция. Сам по себе пустой внешний catch не доказывает отсутствие сообщения; исправление должно устранять молчаливый отказ, а не плодить дубли уведомлений.
- Исходная форма шаблона содержит технический тип `custom_document`. Проверить конечный DOM и реальный пользовательский путь; если внутренний код виден обычному пользователю, заменить понятным выбором/автоподстановкой с доступным редким расширением.
- Навигация и окна увеличиваются после загрузки модулей. Проверить мобильное переполнение, доступность всех разделов, длинные подписи, масштабирование, возврат фокуса и положение основного действия.
- Несколько путей загрузки и повторной обработки должны показывать один и тот же подтверждённый статус файла. Не ломать уже существующее различение частичного успеха и неизменяемого источника.
- Повторный рендер/MutationObserver/таймер не должен стирать ввод, создавать дубликат кнопки, перескакивать к другой записи или считать программную подстановку действием пользователя. Сначала воспроизведение на конкретном элементе; затем минимальное исправление.

### Что сохранять, а не разрабатывать заново

Прямое «Выполнено», необязательные материалы, сохранение контекста поиска, минимальное создание заседания, продолжение календарь → план для 0/1/N планов, пакетный импорт с независимыми ошибками, архив вместо потери истории, ручной приоритет над извлечением, автономность и необязательная ЛЛМ уже являются действующими контрактами. Дизайнер не должен повторно добавлять подтверждения, обязательные справки, лишний выбор даты или параллельные редакторы.

## 6. Очередь работ и зависимости

### R0. Замкнуть реестр на реально отображаемый интерфейс

Владелец: координатор + все D-зоны + независимый аудитор. Вход: точный source-index и текущий код. Для каждого элемента найти отображение, инициатор, обработчик и результат; для каждой формы раскрыть варианты new/edit/read-only/empty/error по реальной логике. Все динамические option/шаблонные строки раскрыть на конечном наборе эквивалентных классов данных. Отдельно пройти программные узлы и селекторы-кандидаты.

Проверять на изолированной тестовой базе. Не выполнять слепой обход кликами по рабочей установке: он может удалить данные, изменить права или отправить сообщения. Для подтверждённо неинтерактивного кандидата записать основание; для недостижимого кода — входы и доказательство. Не считать его успешно проверенным экраном.

Выход: у всех записей есть конкретный сценарий/варианты, владелец, применимость состояний и решение. Неизвестное остаётся открытым. Только после этого фиксировать окончательный знаменатель браузерной приёмки.

### R1. Общие правила без переписывания приложения

Владелец D1; D7 участвует в безопасности/входе; аудитор проверяет независимо. Приоритет P0/P1.

Определить единое поведение кнопок, формы, окна, инспектора, локальной ошибки, загрузки, пустого состояния и уведомления, используя существующие компоненты и CSS. Исправлять общий компонент/токен вместо сотен локальных вариантов. Проверить клавиатуру, закрытие, возврат к контексту и отсутствие двойной отправки. Парольные prompt вынести в отдельный ограниченный сценарий D7 с профильной проверкой безопасности.

Критерий: повторное открытие/закрытие каждого затронутого окна, Tab/Shift+Tab/Escape, ошибка/повтор и узкий экран работают одинаково; различия предметных подтверждений сохранены. Геометрия не зависит от статистики использования.

### R2. Документ → рабочий объект → выполнение

После R1 параллельно D2 и D4, с единым владельцем общего инспектора. Приоритет P1.

Пройти все формы загрузки, распознавания, предпросмотра, шаблона и исходной строки; затем все кнопки планов, поручений, распоряжений, материалов и План / факт. Завершить путь от исходного файла до сохранённого результата и обратной навигации. Исправлять только неоднозначности; ошибки одного файла/строки не блокируют остальные. Даты/исполнители/контекст не запрашиваются повторно без причины.

Критерий: новое/импортированное значение после перезагрузки открывается в правильном объекте; «Выполнено»/«Вернуть в работу» синхронизируют проекции; материал остаётся необязательным; архив/повтор не уничтожают ручную правку и историю.

### R3. Заседания и массовые протоколы

D3 после общего контракта R1, параллельно с R2 в своих файлах. Приоритет P1.

Каждая кнопка повестки, реквизитов, переноса, исходника, генерации, пакетного выбора, массовой правки, повторного распознавания, формата и библиотеки шаблонов проходит отдельное задание. Проверить частичное сохранение, устаревшую строку, отмену, архив источника отдельно от заседания, длинную повестку и все вопросы/решения в итоговом документе. Реальные неполные даты берутся из загруженного документа, а не из текущего календаря или демонстрационного примера.

Критерий: перенос/правка/повтор не создают дубликаты и не возвращают удалённые вопросы; итоговый документ содержит выбранный набор полностью; рабочее заседание переживает архивирование источника.

### R4. Научная и учебная работа

D5 и D6 после R1; зависят от общего документного intake R2. Приоритет P1/P2.

Проверить все формы импорта/сопоставления, реестры, жизненные циклы, связи с планом, шаблоны и выдачу отчёта. Для учебных ведомостей отдельно пройти выбор группы/периода, неоднозначные столбцы, неверную оценку, историю загрузок, архив/восстановление, дисциплину и сводку по выбранным источникам. Дизайнер не меняет формулу показателя ради более красивой карточки.

Критерий: пользователь видит, какие источники вошли в результат; ошибочные строки исправимы независимо; текущий результат не подменён неуспешной или архивной загрузкой; все предлагаемые приложением форматы действительно выдаются.

### R5. Настройки, доступ и необязательные интеграции

D7; общие меню согласуются с D1, изменения безопасности — по действующим риск-правилам. Приоритет P0/P1.

Пройти все состояния PIN и парольного режима, профиль, сотрудников/роли, доступ к объекту, оргструктуру/должности/назначения, импорт из Оформлятора, настройки доставки, тест и отключение канала. Не сохранять код удалённого сервиса или секрет в подстановках. Проверять отсутствие внешней системы, неверный сервис, отказ доступа, пустую группу и частичный импорт.

Тест внешней доставки выполнять только на согласованном тестовом получателе либо через изолированную заглушку; обычный дизайнерский прогон не отправляет реальные сообщения. При недоступности интеграции локальные справочники, календарь и документы продолжают работать.

### R6. Сквозная доводка всего реестра

Координатор + D1, все предметные владельцы и независимый аудитор. После R2–R5. Приоритет P2; анимация P3 только при пользе.

Для каждой строки ведомостей проверить итоговую типографику, плотность, последовательность действий, русский текст, длинные значения и адаптивность. Убрать только доказанно лишние контейнеры/плашки/иконки. Taste ограничен согласованными токенами; одна выбранная система записывается в `docs/design.md`. Emil проверяет только реально используемое движение; анимация не является условием красоты или готовности.

Сквозные пути: поиск → объект → правка → возврат; календарь → план → поручение → выполнение → План / факт; протокол → заседание → перенос → выпуск; документ → распознавание → исключение → повтор; архив → восстановление → прежние связи; научная/учебная загрузка → исправление → отчёт. Проверить уход между разделами во время обработки, смену роли, второй таб и устаревший ответ.

### R7. Закрытие по доказательствам

Независимый аудитор и tests. По каждой записи: сохранить / исправить / объединить / удалить с основанием, результат применимых проверок, ссылка на тест/снимок/трассу и commit. Остаток не маскировать общим PASS. Целевые браузерные проверки дополняют существующие suites; полный регресс и целевая Astra-приёмка относятся к последующему выпуску, а не автоматически объявляются выполненными этим планом.

## 7. Правила проверки и завершения

Планируемый охват — все исходные записи и все применимые варианты. Полнота регистрации, полнота задания и фактическая приёмка считаются отдельно. Нельзя приравнять 117 учтённых файлов к 100% проверенного пользовательского поведения.

Работа над зоной закрывается, когда нет элемента без владельца/критерия, окна без перечня вариантов и сценария без устойчивого результата. Для любого `неприменимо` записана причина; для любого `не проверено` остаётся открытое задание. Удаление кнопки не считается исправлением, если необходимое действие стало недоступно.

Изменение `public/**` или серверного HTML-сборщика требует обновления индекса и проверки появившихся/исчезнувших записей. Не переносить автоматически старый PASS на изменённый код. Сведения об испытаниях хранятся отдельно от автоматически создаваемого исходного каталога.

В каждом задании сначала выполнить узкие проверки, затем релевантный проектный набор. Существующие проверки выбирать по FLOWS; наличие файла теста не означает покрытия всех перечисленных состояний. Новые тесты должны проверять наблюдаемое поведение и данные, а не только наличие слов в Markdown.
