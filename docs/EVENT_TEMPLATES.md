# Визуальные шаблоны мероприятий и подбор для кафедры

Продолжение [разноуровневых планов](MULTILEVEL_PLANS.md), задача [#375](https://github.com/f2re/kafedra-planner/issues/375). Исходная версия: `main@b1e60af895e6918f8938e9c54bf3ee7e2cee76be`, схема 32. Изменение добавляет схему **33**, не меняя номер приложения. Сборщик runtime-архива включает новый интерфейс, API, LLM-модули и migrations из текущего исходного кода. Опубликованные ранее установщики не обновляются при merge в `main`; отдельный новый выпуск этим изменением не публикуется.

## Рабочий сценарий

Оператор открывает **Планы → Мероприятия и план на месяц**, выбирает месяц и указывает кафедру. Сначала можно использовать стандартные поля, затем сохранить собственный шаблон и применять его каждый месяц.

В **Поля и вид документа** рядом с настройками виден предварительный вид таблицы. Название мероприятия и срок обязательны, исполнитель необязателен. Место есть в начальном наборе. Поля можно переименовать, переставить, изменить их ширину и видимость; дополнительные поля имеют тип «Текст», «Дата», «Число» или «Список». Пользователь выбирает книжную или альбомную страницу и нумерацию строк. Пример использует доступные мероприятия; при их отсутствии показываются пустые ячейки, а не выдуманные деловые данные.

**Подобрать и заполнить** рассматривает доступные мероприятия выбранного месяца, в том числе из планов института. Принадлежность исходника институту сама по себе не исключает мероприятие: в нём может быть явно названа кафедра. Результат содержит рекомендуемые строки, строки для уточнения и остальные. Для каждой рекомендации показано основание и выдержка источника. Подбор не скрывает записи по предположению и не меняет исходные мероприятия.

Оператор проверяет предварительный состав, снимает или добавляет отметки и принимает выбранные строки. Во время просмотра подбора показано одно действие принятия; **К списку мероприятий** возвращает ручной список с сохранёнными отметками. Полученный месячный черновик уже содержит доступные поля и подтверждённые источником предложения заполнения. Во вкладке **В плане** можно уточнить печатные значения и скачать DOCX. Сохранённый состав открывается повторно. Незаполненные обязательные поля показываются с указанием строки до публикации документа; неизвестный срок не заменяется сегодняшней датой.

## Где хранятся поля

| Сведения | Источник истины | Что изменяет правка |
| --- | --- | --- |
| Название, фактические сроки, исполнитель | Существующий `plan_item` | Штатная правка исходного плана |
| Место и дополнительные значения | `plan_item_details`, одна запись на мероприятие | Данные мероприятия, видимые в других месячных составах |
| Печатная формулировка, срок, место и дополнительные значения | Overrides в `monthly_plan_items` | Только выбранный месячный документ |
| Поля и вид таблицы | Неизменяемая версия `plan_event_template_versions` | Новая версия шаблона для явно выбранных составов |
| Предварительный подбор | Неизменяемый `plan_event_selection_runs` | Предложения до принятия оператором |
| Готовый файл | Существующий `monthly_plan_exports` и неизменяемый документ | Новый снимок при изменившемся составе |

Дополнительное поле имеет постоянный ключ, независимый от подписи и положения. Переименование не теряет значения; удаление поля из новой версии не удаляет сохранённые значения и старые документы. Тип существующего ключа не меняется: для другого типа создаётся новое поле. Даты дополнительных полей проверяются как реальные календарные даты, числа и значения списков проверяются сервером.

Изменение данных мероприятия требует права редактирования исходного пункта. Печатные изменения доступны владельцу месячного состава при сохранённом праве чтения исходника. Ручные значения не выдаются за автоматически извлечённые факты; их история сохраняется в журнале изменений. Смена шаблона и печать не создают новых пунктов плана, задач или календарных записей.

## Шаблон и DOCX-образец

Визуальный шаблон задаёт **таблицу**, а необязательный загруженный DOCX-образец — **шапку, подписи и остальное оформление документа**.

Без образца формируется обычный редактируемый DOCX с выбранными колонками. При сочетании с образцом генератор сохраняет его пакет OOXML, колонтитулы и окружающий текст, штатно заменяет месяц и заменяет только выбранную таблицу таблицей из визуального шаблона. Ориентация и поля страницы применяются к секции этой таблицы. Старый способ выгрузки по образцу без визуального шаблона продолжает работать.

Если визуальный шаблон не выбран, стандартная таблица добавляет колонку места, когда оно заполнено хотя бы у одной строки. В старом DOCX-образце без настройки места значение выводится с подписью «Место:» в описании, результате или, если таких колонок нет, в названии мероприятия. Сохранённое место не теряется при смене способа выгрузки.

Месячный состав ссылается на точную версию полей. Сохранение новой версии шаблона не подменяет ранее выбранную версию и не меняет старые DOCX. Перед генерацией фиксируются версия полей, версия DOCX-образца, порядок, канонические данные, печатные значения и сведения о принятом подборе. После асинхронного формирования файла доступ и снимок повторно проверяются; изменение источника останавливает публикацию устаревшего документа.

Предварительный вид показывает структуру таблицы и значения. Он не является точным постраничным рендером Word: переносы страниц зависят от офисного приложения и установленных шрифтов.

## Как работает подбор

1. Сервер получает кандидатов из существующего общего реестра после проверки прав. Ограничивает период, выбранные фильтры и объём обработки. Строгий текстовый фильтр кафедры не используется для предварительного исключения кандидатов.
2. Детерминированная часть отмечает явное совпадение кафедры в названии плана, владельце, исполнителе или тексте мероприятия. Совпадение сопровождается конкретным основанием, а не утверждением об официальной оргпринадлежности.
3. Если локальная LLM включена, она получает ограниченные порции кандидатов и исходных фрагментов. Ответ содержит только известные идентификаторы, категории рекомендации, основание и цитату. Инструкции внутри документов рассматриваются как текст, модель не получает инструментов записи.
4. Каждое предложение поля проверяется по одному исходному фрагменту. Место и дополнительные значения предлагаются только при наличии основания; уже заполненные ручные данные не подменяются. Реальные даты, название и исполнитель скрыто не переписываются.
5. Результат сохраняется сервером с параметрами, методом, моделью, хешами и источниками. Клиент передаёт при принятии идентификатор этого результата и выбранные мероприятия, а не произвольное «доверенное» доказательство.
6. При принятии повторно проверяются владелец результата, права, версия шаблона, месяц и актуальность каждого источника. Устаревший или недоступный пункт получает отдельную ошибку; остальные пригодные пункты сохраняются. Повтор не переписывает уже добавленные или вручную изменённые строки.

Недоступность модели, тайм-аут, некорректный JSON или неподтверждённые значения оставляют доступным детерминированный результат. Интерфейс сообщает фактический способ подбора. Ограниченная порция не объявляется полным анализом архива; наличие продолжения показывается явно. Отмена или смена месяца не позволяет позднему ответу заполнить другой документ.

## Хранение и API

Добавочная миграция `033_event_templates.sql` создаёт `plan_event_templates`, `plan_event_template_versions`, `plan_item_details`, `plan_event_selection_runs` и добавляет ссылки и поля месячного состава. Ранее применённые миграции не изменяются. Версии шаблонов и результаты подбора защищены от перезаписи; принятые сведения о подборе также сохраняются отдельно от ручных печатных правок.

| Метод | Путь | Назначение |
| --- | --- | --- |
| GET / POST | `/api/event-templates` | Список и создание визуальных шаблонов |
| GET | `/api/event-templates/:id` | Шаблон и его версии |
| POST | `/api/event-templates/:id/versions` | Новая версия с контролем ожидаемой версии |
| GET / PATCH | `/api/plan-events/:id/details` | Каноническое место и дополнительные значения с ревизией |
| POST | `/api/plan-events/suggest` | Сохранённый предварительный подбор и заполнение |
| POST | `/api/monthly-plans/:id/apply-suggestion` | Принятие выбранных строк сохранённого подбора |
| POST / PATCH | `/api/monthly-plans` и `/api/monthly-plans/:id` | Состав, кафедра, точная версия визуального шаблона и DOCX-образец |
| PATCH | `/api/monthly-plans/:id/items/:itemId` | Печатные изменения строки |
| POST | `/api/monthly-plans/:id/export` | Проверка обязательных полей и неизменяемый DOCX |

## Проверка и границы

Независимая визуальная приёмка и замечания: [`event-template-acceptance.md`](design/event-template-acceptance.md). Точные runtime-промпты, JSON Schema и диагностические запросы задач `plan-extract-v1` и `plan-department-selection-v1` входят в общий каталог 15 задач: [`AGENTS_AND_REMOTE_LLM.md`](AGENTS_AND_REMOTE_LLM.md). Отдельный архив каталога содержит описание задач и диагностический клиент; модель GGUF и сервер в него не входят.

Целевые тесты проверяют валидацию и версии полей, сохранение канонических значений, отсутствие календарных дублей, частичные результаты и повторное принятие, недоступные и устаревшие источники, строгие цитаты, ошибку модели и автономный путь. DOCX проверяется по составу архива и содержимому таблицы, включая скрытые поля, нулевые значения, пустого исполнителя, сохранение старой версии шаблона и сочетание с загруженным образцом.

Изменение схемы проверяется на чистой установке, обновлении, повторном запуске, целостности, резервном копировании, восстановлении и принудительном отказе миграции. Браузерная проверка охватывает широкий и узкий экраны, создание и повторное использование шаблона, предварительный подбор, ручную правку и выгрузку. Фактические результаты и exact SHA фиксируются в PR.

Тестовые HTTP-ответы модели доказывают программный контракт, но не качество конкретной GGUF-модели. Его предметная оценка требует настоящих планов разных уровней и выбранной локальной модели. Сходные обязательства разных документов не сливаются автоматически; состав следующего месяца не создаётся по расписанию.
