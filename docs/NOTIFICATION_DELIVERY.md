# Персональная доставка уведомлений

## Назначение

Внутренний центр уведомлений остаётся обязательным и работает без Интернета, SMTP и Telegram. Внешняя доставка — дополнительный канал для случаев, когда сотрудник не держит интерфейс открытым.

Источник уведомления не меняется: система использует те же персональные сроки, отчёты и рассчитанные риски, которые видны в интерфейсе. Повторный запуск worker не создаёт новое сообщение для того же уведомления, сотрудника и канала.

## Что отправляется

Исполнителю внешне отправляются только актуальные события, которые требуют действия: напоминание по сроку, срок сегодня, просрочка, возврат на доработку и персональный риск выполнения.

Руководителю обычные напоминания сотрудника не дублируются. Внешне передаются только:

- материал, ожидающий проверки руководителем;
- рассчитанный риск срыва, просрочка или возврат на доработку в его зоне контроля.

Если для одного обязательства одновременно существует обычная просрочка и более содержательный `plan/fact`-риск, наружу уходит один риск, а не два почти одинаковых сообщения.

## Каналы

### SMTP

SMTP реализован штатными модулями Node.js и не добавляет runtime npm-зависимостей. Поддерживаются:

- локальный relay по обычному TCP;
- STARTTLS;
- обязательный STARTTLS;
- SMTPS с TLS с момента подключения;
- AUTH PLAIN и LOGIN;
- проверка сертификата сервера;
- UTF-8 тема и текст письма;
- устойчивый `Message-ID` для повторной попытки одного outbox-сообщения.

Минимальная конфигурация локального relay:

```env
KAFEDRA_NOTIFICATION_DELIVERY_ENABLED=true
KAFEDRA_SMTP_HOST=127.0.0.1
KAFEDRA_SMTP_PORT=25
KAFEDRA_SMTP_FROM=kafedra@organization.local
```

Для сетевого SMTP рекомендуется требовать TLS:

```env
KAFEDRA_SMTP_HOST=mail.organization.local
KAFEDRA_SMTP_PORT=587
KAFEDRA_SMTP_STARTTLS=true
KAFEDRA_SMTP_REQUIRE_TLS=true
KAFEDRA_SMTP_REJECT_UNAUTHORIZED=true
KAFEDRA_SMTP_USERNAME=kafedra
KAFEDRA_SMTP_PASSWORD=...
KAFEDRA_SMTP_FROM=kafedra@organization.local
```

Для implicit TLS обычно используются:

```env
KAFEDRA_SMTP_PORT=465
KAFEDRA_SMTP_SECURE=true
```

### Telegram

Telegram является полностью необязательным внешним адаптером. Основная система от него не зависит.

```env
KAFEDRA_NOTIFICATION_DELIVERY_ENABLED=true
KAFEDRA_TELEGRAM_BOT_TOKEN=...
```

По умолчанию используется официальный Bot API. Для контролируемой инфраструктуры базовый адрес можно заменить:

```env
KAFEDRA_TELEGRAM_API_BASE=https://api.telegram.org
```

Токен бота никогда не сохраняется в SQLite, журнале аудита или пользовательском профиле.

## Персональные настройки

После входа сотрудник открывает меню своего аккаунта → `Доставка уведомлений`.

Доступны:

- почта и собственный адрес;
- Telegram и собственный ID чата;
- немедленная доставка существенных событий;
- ежедневная сводка;
- еженедельная сводка;
- тихие часы;
- часовой пояс.

Клиент не передаёт доверенный `personId`: профиль определяется серверной сессией. Сотрудник не может изменить канал другого сотрудника прямым запросом.

Если администратор не настроил внешний провайдер или полностью отключил внешнюю доставку, профиль можно сохранить заранее. Внутренние уведомления продолжают работать как раньше, а outbox не выполняет сетевых вызовов.

## Тихие часы и сводки

Тихие часы не удаляют уведомление. Для созданной доставки рассчитывается `available_at`, и существующая очередь worker забирает сообщение после окончания тихого периода.

Ежедневная сводка имеет один идемпотентный ключ на локальную календарную дату, еженедельная — один ключ на неделю. Поэтому повторный sweep не создаёт дубликат дайджеста.

Часовой пояс хранится как IANA zone, например `Europe/Moscow`, `Europe/London`, `Asia/Vladivostok`.

## Outbox и повторные попытки

`notification_deliveries` — transactional outbox поверх существующей очереди `jobs`.

Ключ уникальности:

```text
workspace + сотрудник + notification_key + канал
```

Worker использует существующие lease, `max_attempts`, exponential backoff и восстановление после аварийного завершения. Ошибка одной доставки не останавливает обработку документов или другие сообщения.

Администратор в той же панели видит состояние очереди и последние ошибки. После исправления SMTP/Telegram можно нажать `Повторить`; создаётся новая ревизия попытки с отдельным idempotency key, но исходная запись outbox и история аудита сохраняются.

## Статусы

- `created` — сообщение создано и ожидает отправки;
- `sent` — SMTP relay принял письмо. Это не трактуется как доказанная доставка в почтовый ящик;
- `delivered` — Telegram Bot API принял сообщение и вернул его ID;
- `confirmed` — адресат прочитал или скрыл соответствующее уведомление в Kafedra Planner;
- `error` — последняя попытка внешнего канала завершилась ошибкой.

Такое разделение не выдаёт принятие письма SMTP-сервером за фактическое прочтение получателем.

## Секреты и аудит

SMTP-пароль и Telegram token читаются только из конфигурации процесса. В журнале фиксируются:

- ID outbox-сообщения;
- канал;
- вид доставки;
- результат;
- ошибка;
- маскированный адресат.

Секрет провайдера не входит в БД или audit log.

Файл `/etc/kafedra-planner/kafedra-planner.env` должен оставаться `0640 root:kafedra-planner`, как и в штатном установщике.

## Проверка после настройки

1. Включить канал в системной конфигурации и перезапустить worker.
2. Войти под сотрудником и сохранить персональный канал.
3. Создать тестовую задачу со сроком и напоминанием.
4. Убедиться, что внутреннее уведомление появилось независимо от внешнего канала.
5. Проверить административную диагностику доставки.
6. При искусственной ошибке канала убедиться, что статус становится `error`, а ручной `Повторить` возвращает запись в очередь без дублирования исходного уведомления.
