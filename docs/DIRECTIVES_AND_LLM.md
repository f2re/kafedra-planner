# Распорядительные документы и локальная модель

## Основной принцип

Указ, распоряжение и приказ обрабатываются полностью без LLM. Детерминированный разбор является источником предметных данных; локальная модель может только предложить оператору дополнительную структуру для проверки.

Недоступность, таймаут, неверный JSON или выдуманная ссылка модели не меняют сохранённый документ, поручения, календарь или подтверждённые сведения.

## Детерминированный разбор

Поддерживаются `указ` (`decree`), `распоряжение` (`directive`) и `приказ` (`order`). Из шапки извлекаются вид, номер, дата, заголовок и издатель. Дата основания ищется только до распорядительной части: срок поручения не может молча стать датой документа.

Распорядительная часть определяется по явным маркерам `ПРИКАЗЫВАЮ`, `РАСПОРЯЖАЮСЬ`, `ПОРУЧАЮ`, `ОБЯЗЫВАЮ`, `ПОСТАНОВЛЯЮ`. Нумерованные пункты сохраняют номера. Для ненумерованного документа fallback принимает только строки с явным действием; подписи, строки ознакомления и служебные хвосты не превращаются в поручения.

Для поручения сохраняются исходный номер, текст, срок, основной исполнитель, соисполнители, контролирующий, направление, ожидаемый результат и признаки отчётности. Соисполнитель хранится отдельной ролью `coexecutor`.

## Доказательства и частичный импорт

Исходный документ и его версия неизменяемы. Реквизиты документа имеют line locator; поручение хранит диапазон исходных строк и отдельные локаторы срока, основного исполнителя, соисполнителей и контролирующего.

Неоднозначность одной строки не блокирует документ:

- нет срока — поручение сохраняется, создаётся `due_date_missing`, календарный срок не выдумывается;
- нет основного исполнителя — создаётся `executor_missing`;
- сотрудник не сопоставился точно со справочником — raw ФИО сохраняется и создаётся review;
- остальные корректные пункты продолжают импортироваться.

Повторное сохранение одной версии документа возвращает уже существующее основание и не создаёт второй набор поручений, исполнителей или календарных записей.

## Сопоставление людей

Автоматически применяется только точное нормализованное совпадение со справочником `people`. Однофамилец не выбирается по догадке. Основной исполнитель, соисполнитель и контролирующий хранятся отдельными ролями; фасетный поиск по исполнителю учитывает все роли.

## Необязательный llama.cpp

При `KAFEDRA_LLM_ENABLED=true` worker после детерминированного разбора вызывает совместимый `/v1/chat/completions` локального `llama.cpp`. Задача `directive-v3` описана в `packages/ai/src/directive-task.mjs`: инструкция, схема, предел ответа и хэши. Клиент принимает корневой адрес и адрес с окончанием `/v1`; адреса с паролем, query или fragment отклоняются, перенаправления не выполняются.

Разрешена только фиксированная структура JSON: реквизиты документа и `assignments[]` с `itemNo`, `title`, `instructionText`, `dueDate`, `executors`, `controller`, `expectedResult`, `sourceQuote`. Неизвестные поля, неверные типы и невозможные ISO-даты отклоняются.

Для каждого предложенного поручения `sourceQuote` обязателен и проверяется по исходному тексту с нормализацией регистра и пробелов. Цитата, которой нет в документе, переводит запуск в `failed / llm_unverified_proposal`. Наличие цитаты не доказывает правильность всех остальных предложенных реквизитов: их по-прежнему проверяет оператор.

Запрос задаёт `stream=false`, `temperature=0`, `chat_template_kwargs.enable_thinking=false` и JSON Schema через `response_format`. При HTTP 400/422 допускается ровно один повтор без `response_format` в пределах того же тайм-аута. Состав полей остаётся в системной инструкции и без поддержки схемы сервером. Принимается только полный JSON или целиком ограждённый JSON-блок, а не объект, найденный внутри рассуждений. Обрезанный ответ, вызов инструмента и слишком большой HTTP-ответ отклоняются.

Выход ограничен минимумом настройки и 2048 токенов. Вход проверяется консервативным пределом UTF-8-байтов по настроенному контексту с резервом для выхода и служебного текста. Это не точный подсчёт токенизатором Qwen. Слишком длинный документ или большой детерминированный результат дают `llm_context_too_small` до сетевого запроса; исходник не обрезается молча. Основной разбор продолжает работать. Разбор длинных документов частями в эту задачу не входит.

Даже успешно проверенный JSON не применяется автоматически: создаётся review `llm_directive_proposal`. В текущем `processor.mjs` вызов модели ожидается **до транзакции сохранения результатов разбора**, а не в отдельной очереди обогащения. Поэтому медленная модель задерживает появление рабочего объекта распоряжения. Этот клиентский патч не меняет порядок транзакций и устойчивую очередь; устранение задержки относится к #88.

## Журнал LLM

Каждый запуск сохраняет локально purpose, санитизированный endpoint, модель, версию prompt, SHA-256 входного текста, статус, структурированный ответ или ограниченный диагностический ответ, безопасный код ошибки и длительность.

Дополнительные хэши системной инструкции и входного JSON возвращаются клиентом как `metadata` и включаются в прикладную диагностику. Существующая запись `llm_runs` эти дополнительные поля пока не сохраняет; новая история или миграция здесь не вводится.

Credentials и query-параметры endpoint, а также сырой текст сетевого исключения в журнал не переносятся. Сетевые ошибки нормализуются в стабильные коды (`llm_request_failed`, `llm_timeout`, `llm_http_...`).

## Проверяемые режимы

Автоматические тесты проверяют отключённую модель без сети, нормальный ответ, строгий JSON, реальные цитаты, невозможные даты, отказ HTTP, ограниченный повтор, тайм-аут тела ответа, предел входа/выхода, отказ от инструментальных вызовов и одинаковую обработку root/`/v1`.

Прикладная проверка установленного сервера: `node scripts/llm-acceptance.mjs` с действующими `KAFEDRA_LLM_*` в окружении. Она вызывает клиенты на синтетических заседании, статье, отчёте и распоряжении; рабочую БД не открывает. Отключённая модель, пустая или частичная подборка не считаются успешной приёмкой. Отчёт — JSON, код возврата успешной проверки — 0.

LLM не является источником истины и не является обязательной частью эксплуатации.

## Автономная поставка llama.cpp

Для Astra Linux/Debian доступен отдельный full-offline вариант, который включает локальный `llama-server` и одну или несколько GGUF-моделей. Большие runtime/model-файлы не хранятся в Git: их добавляет release-сборщик, фиксируя SHA-256 в отдельном LLM manifest и общем manifest bundle.

Managed service слушает только `127.0.0.1`, проверяется через `/health` и `/v1/models` и может быть отключён без изменения предметных данных. Обычный full bundle и вся детерминированная функциональность остаются независимыми от LLM.

Для внешнего LLM Offline Bundle используется `KAFEDRA_LLM_MANAGED=false`: второй экземпляр модели не нужен. Инструкция: [`LLAMA_OFFLINE_DEPLOYMENT.md`](LLAMA_OFFLINE_DEPLOYMENT.md). Сверка комплекта astra7 и ограничения сценариев: [`аудит совместимости`](audits/2026-10-07-llm-offline-compatibility.md).
