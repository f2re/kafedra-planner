# Обучаемые пользовательские значения по умолчанию

## Задача

Интерфейс сокращает повторный ручной ввод, но остаётся визуально стабильным. Система обучается только на **явных выборах человека** и использует накопленную частоту как безопасную подсказку для следующего аналогичного действия.

Preference-layer действует во всём операторском интерфейсе. Это не рекомендательная система и не источник предметных фактов. Ошибка этого слоя не должна мешать сохранить задачу, заседание, документ, поручение, план или шаблон.

## Четыре режима адаптации

### `safe-default`

Используется при создании нового объекта, когда повторение значения безопасно. Частый вариант может стать значением по умолчанию, а варианты в `select` ранжируются.

Примеры: тип новой календарной записи, категория, важность, напоминание, вид периода периодической задачи, направление, исполнитель, председатель и секретарь при отсутствии сохранённой настройки.

### `rank-only`

Используется в фильтрах и при редактировании уже существующих объектов. Частые варианты поднимаются внутри списка, но текущее/сохранённое/нейтральное значение не заменяется автоматически.

Примеры: структурированные фильтры планов, поиска, науки и plan/fact; исполнитель и контролирующий уже существующего поручения; направление существующего пункта плана.

### `domain-derived`

Предметная автоматика сильнее статистики. Если система надёжно знает значение из текущего контекста, frequency default не применяется.

Примеры:

- клик по конкретному дню календаря;
- дата и поля существующего объекта;
- руководитель, найденный по организационной структуре сотрудника;
- следующий период плана, вычисленный из текущего образца;
- перенесённые даты сформированного плана;
- специфическая эвристика шаблона: `Дата:` остаётся типом `date`, даже если пользователь чаще создаёт текстовые поля.

### `never-learn`

Частотная автоматика запрещена для:

- паролей, токенов, логинов и секретов;
- поисковых запросов и произвольного свободного текста;
- названий документов, событий, задач, вопросов, решений и отчётов;
- ролей аккаунтов, ACL, владельцев и уровня доступа;
- действий `подтвердить / вернуть / отклонить / удалить`;
- любых значений, где автоматический выбор может изменить полномочия или предметное решение.

## Что никогда не меняется от частоты

- расположение кнопок;
- порядок вкладок и разделов;
- расположение основных полей формы;
- наличие обязательных проверок;
- права доступа;
- уже сохранённое значение существующего объекта.

Поэтому интерфейс не «плывёт» между открытиями страницы. Внутри `select` placeholder и нейтральные варианты остаются на логическом месте, а рабочие варианты могут ранжироваться по персональной частоте.

## Даты

Абсолютная дата не является обучаемым значением. Нельзя сохранить `2026-09-01` и через месяц продолжать предлагать её пользователю.

Для безопасных новых действий хранится относительное значение:

```text
d:0    сегодня / базовая дата
d:7    через 7 дней
d:-1   за день до базовой даты
none   обычно оставлять пустым, если поле необязательное
```

Базовая дата зависит от контекста:

- новая календарная запись, созданная общей кнопкой `Создать` — текущий день;
- новое заседание — текущий день;
- начало периодической задачи — текущий день;
- контрольный срок периодической задачи — выбранная дата начала, а при её отсутствии текущий день.

Клик `+` внутри конкретного дня календаря является явным контекстом и всегда важнее learned offset. Существующая дата объекта также всегда важнее статистики.

Сервер ограничивает допустимый диапазон смещений, поэтому повреждённое или намеренно чрезмерное значение не становится default.

## Люди

Частота выбора человека хранится по смысловой роли, а не глобально для всех списков.

Например, частый исполнитель может ранжироваться выше в выборе исполнителя, но не становится из-за этого председателем заседания. Первые роли:

- председатель заседания;
- секретарь заседания;
- исполнитель периодической задачи;
- руководитель/контролирующий;
- исполнитель и контролирующий поручения;
- текущий рабочий профиль manager/admin.

Для `staff` текущий профиль всегда определяется аккаунтом и не переопределяется статистикой.

## Фильтры

Фильтры делятся по устройству управления:

- в обычном `select` частые рабочие варианты ранжируются, но нейтральный `Все / Не важно / Везде` остаётся выбранным по умолчанию;
- композитные видимые фильтры календаря могут восстановить наиболее частое явно выбранное состояние, потому что активные кнопки постоянно видны оператору и меняются одним нажатием;
- поисковый текст и текстовые фасеты не обучаются.

Сохранённый вид plan/fact остаётся отдельным осознанным механизмом и не подменяется preference-layer.

## Шаблоны

Для нового поля обучаются:

- тип значения;
- стратегия извлечения;
- обязательность.

Но конкретная детерминированная эвристика документа сильнее общего fallback. Например, строка с двоеточием сохраняет специфическую стратегию `после подписи`, а поле с явным признаком даты — тип `date`. Frequency default применяется там, где текущая эвристика оставила общий `string/line` fallback.

## Периодические задачи

Обучаются безопасные значения нового действия:

- исполнитель;
- вид периода;
- направление;
- относительное начало;
- относительный контрольный срок.

`periodKey` не запоминается как старый текст периода. После выбора частого вида периода он вычисляется из текущей даты: календарный год, квартал, семестр или учебный год. Ручной `custom` остаётся ручным.

Руководитель сотрудника, найденный по структуре, имеет приоритет над learned manager.

## Когда увеличивается частота

Для сохраняемого предметного действия частота увеличивается только если одновременно выполнены условия:

1. пользователь действительно изменил контрол;
2. основное действие успешно завершилось;
3. значение входит в серверный allowlist;
4. это не повторная доставка того же `interactionId` для того же контекста.

Для чистого UI-режима или фильтра, не изменяющего предметные данные, завершённым действием считается сам trusted-выбор пользователя.

Если форма открылась с автоматически предложенным значением и пользователь просто нажал `Сохранить`, частота этого значения не изменяется. Синтетические DOM-события и программные подстановки также не считаются действиями человека.

Явный выбор в текущем сеансе немедленно становится текущим и не должен «отскакивать» обратно к статистическому лидеру после записи preference.

## Приоритет значения

```text
сохранённое значение существующего объекта / предметный контекст
        ↓
явный выбор пользователя в текущем действии
        ↓
надёжная domain-derived автоматика
        ↓
персональный самый частый safe-default
        ↓
статический безопасный fallback продукта
```

Для `rank-only` learned значение не занимает место текущего значения: статистика меняет только порядок рабочих вариантов внутри списка.

## Хранение

`ui_choice_preferences` хранит по одной компактной строке на явный выбор:

- workspace;
- account;
- разрешённый context key;
- выбранное значение;
- `interaction_id` пользовательского действия;
- время выбора.

Первичный ключ `workspace + account + context + interaction_id` делает повторную доставку одного действия идемпотентной. Частота вычисляется обычным `COUNT(*)` по значениям, а время последнего выбора — `MAX(selected_at)`. Отдельный журнал и агрегированный счётчик не нужны.

Предпочтения не записываются в предметный аудит и не являются доказательствами. Они входят в обычный SQLite backup/restore. При отключённой авторизации browser-helper может использовать локальное хранилище как автономный fallback; в штатной авторизованной эксплуатации источником является серверная персональная статистика.

## Постоянные настройки не дублируются

Профиль доставки уведомлений уже хранит SMTP/Telegram, digest, quiet hours, день/время и timezone как собственную серверную настройку. Preference-layer не должен создавать вторую копию этих значений. То же относится к сохранённым настройкам заседаний и другим устойчивым предметным/персональным конфигурациям: статистика применяется только там, где действительно сокращает повтор нового действия.

## Адаптивный центр действий

`+ Добавить` использует `action.center.action` только как `rank-only` сигнал. Само расположение глобальной кнопки, три места `Рекомендуется`, группы действий, зона загрузки документа и основные controls остаются фиксированными. Частота может изменить только порядок уже доступных безопасных действий внутри этих фиксированных зон.

Выбор действия записывается только после успешного завершения соответствующего пользовательского сценария. Простое открытие формы, отмена, программный `click()` и автоматическая маршрутизация загруженного документа не увеличивают частоту. Сервер принимает только известные action IDs из allowlist.

Приоритет рекомендаций лексикографический:

```text
явный текущий контекст
→ domain-derived доступность и предметные факты
→ календарный/отчётный период
→ персональная частота action.center.action
→ статический порядок продукта
```

Поэтому клик `+` конкретного дня всегда сохраняет выбранную дату, а распознанный worker-ом план, протокол, распоряжение или научный материал ведёт к точному materialized object независимо от статистики. Такой document route относится к `domain-derived`: он не является пользовательским предпочтением и не обучается.

Если preference-layer недоступен, центр действий показывает тот же статический каталог и продолжает запускать обычные предметные формы. Ошибка preference-layer никогда не блокирует immutable document intake, задачу, событие, план, заседание или другой основной сценарий.
