# GRACE-сценарий: документ сразу становится рабочим объектом

Статус: `implementation`. Родительский пользовательский сценарий: #164.

## Цель

После загрузки одного документа оператор не проходит мастер подтверждения и не ищет созданный объект вручную.

```text
загрузить документ
        ↓
immutable document_version
        ↓
фоновый детерминированный разбор
        ↓
plan или meeting
        ↓
автоматически открыть созданный объект
        ↓
исправить только исключения
```

План, заседание и однозначно извлечённые поля являются рабочими сразу. Подтверждение импорта, утверждение руководителем и обязательный отчёт не добавляются.

## Роли и независимые контуры

### Domain / Data

Проверяет предметный инвариант:

- исходный файл и SHA-256 неизменяемы;
- один `document_version` создаёт не более одного соответствующего плана/заседания;
- повтор обработки не создаёт дубль;
- ошибка одной строки не блокирует остальные;
- ручная правка сильнее повторного машинного предложения;
- проекции можно перестроить из предметных данных.

### UX

Проверяет минимальный путь:

- одиночная загрузка автоматически открывает созданный объект;
- пакетная загрузка не дёргает пользователя между экранами;
- фоновой обработке не нужен блокирующий диалог;
- при задержке показывается только существенное неблокирующее сообщение;
- неоднозначное поле редактируется на месте;
- desktop и mobile выполняют один и тот же предметный сценарий.

### Acceptance

Подтверждает наблюдаемое поведение через Playwright:

- DOCX-план → активный раздел планов → созданный plan;
- документ заседания → активный раздел заседаний → созданный meeting;
- нет кнопок `Подтвердить импорт`, `Утвердить`, `Ожидает подтверждения`;
- неизвестный документ сохраняется и не блокирует интерфейс;
- direct completion из связанной задачи проверяется основным плановым сценарием.

### Release

Проверяет эксплуатационную безопасность:

- миграция не нужна для клиентского моста;
- существующие данные и API не переписываются;
- ошибка удобства не блокирует document intake;
- full CI, backup/restore, offline bundle, systemd install и rollback остаются обязательными перед слиянием;
- post-merge CI выполняется на точном SHA `main`.

## Спецификация поведения

Клиентский мост наблюдает только успешный `POST /api/documents`. Он получает фактический `documentId`, затем ограниченное время проверяет существующие серверные реестры планов и заседаний.

Когда предметный объект найден:

1. создаётся событие `kafedra:intake-object-ready` с `documentId`, видом и `objectId`;
2. при одиночной загрузке открывается соответствующий рабочий раздел;
3. при пакетной загрузке объекты только появляются в реестрах, без принудительного переключения между ними;
4. показывается короткое сообщение, что объект уже создан и доступен для исправления.

Если объект пока не появился, document intake остаётся успешным. Мост прекращает ожидание и сообщает, что обработка продолжается в фоне. Он не создаёт plan/meeting сам и не становится вторым источником истины.

## Ограничения

- не создавать новую таблицу, очередь или предметную сущность;
- не угадывать вид документа на клиенте;
- не считать UI-переход доказательством предметного создания;
- не блокировать загрузку из-за ошибки навигации;
- не открывать случайный ранее созданный план/meeting;
- связывать объект только по фактическому `documentId`;
- не менять ACL, evidence и source links;
- не требовать Интернет, LLM или Оформлятор.

## GRACE gates

### G1 — Spec

- сценарий и запреты зафиксированы в этом документе и issue #164;
- ответственные контуры разделены;
- источник истины и rollback определены.

### G2 — Implementation

- неблокирующий мост добавлен отдельным модулем;
- существующий document intake не заменён;
- plan/meeting ищутся только по source-document identity;
- пакетный и одиночный режимы различаются;
- ошибка моста деградирует только удобство.

### G3 — Acceptance

- unit/integration основного предметного контура зелёные;
- отдельный Playwright desktop/mobile сценарий зелёный;
- полный проектный CI зелёный;
- нет неожиданных pending/skipped/cancelled обязательных jobs.

### G4 — Release / Merge

- PR mergeable, head SHA повторно проверен;
- review threads закрыты;
- squash merge выполнен только после G3;
- новый `main` получен из GitHub API;
- post-merge CI и GRACE workflow успешны;
- issue закрывается только после фактического post-merge evidence.
