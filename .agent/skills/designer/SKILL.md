# Designer — координатор проектирования интерфейса

## 1. Назначение и полномочия

Сначала решить задачу пользователя, затем улучшать оформление. Кафедра-планер — рабочий помощник по документам, планам, поручениям, заседаниям и отчётам, а не рекламный сайт. Система выполняет однозначные операции сама; человек исправляет исключения. Сокращение действий не должно уничтожать данные, скрывать последствия или создавать второй источник истины.

Навык основан на предоставленной пользователем инструкции Designer. Её общие принципы адаптированы к существующему проекту, а не установлены поверх него как новая архитектура. Этот файл — единственная локальная точка маршрутизации дизайна. `AGENTS.md` остаётся главным правилом проекта; `codex/skills/kafedra-workspace-orchestrator/SKILL.md` выбирает предметные навыки. Закреплённые 14 upstream-навыков и их контрольные суммы не изменять для регистрации Designer.

Приоритет: явные требования пользователя → сохранность и функциональность → доступность → предметные контракты и действующая дизайн-система → Impeccable → Taste → анимация. При конфликте предложить минимальное системное исправление, а не менять стек или переписывать всё приложение.

## 2. Автоматическое включение

Прочитать этот файл без отдельной команды при создании, исправлении, аудите или изменении экранов, окон, форм, списков, таблиц, меню, кнопок, текстов интерфейса, HTML/CSS, компоновки, навигации, адаптивности, доступности, переходов и жестов. Формулировки «улучши дизайн», «убери нейрослоп», «проверь UX» также включают этот навык.

Включение координатора не означает запуск всех специалистов. Локальная правка подписи может потребовать только исполнителя и целевой проверки. Изменение сценария требует проектировщика сценария и независимой приёмки. Полный аудит проекта требует полного реестра, но не разрешает массовый редизайн без предметных оснований.

## 3. Маршрутизация навыков

| Задача | Основной маршрут | Ограничение |
|---|---|---|
| Существующий рабочий экран или сценарий | Исследование → `kafedra-flow-intake`/`kafedra-design` → Impeccable при наличии → реализация → независимая проверка | Не начинать с декора и не менять рабочую модель без причины |
| Перегруженные действия и формы | `kafedra-action-recomposition` → `kafedra-design` | Удалять лишние решения, а не прятать обязательные действия |
| Визуальная несогласованность | Действующие токены → Impeccable; Taste только для ограниченного исследования | Taste не определяет жизненный цикл, плотность таблиц, права или логику формы |
| Только анимация | `kafedra-motion`; Emil при наличии подходящего навыка | Не переделывать статический интерфейс; допустим `no-motion` |
| Аудит | Реестр → `kafedra-design-audit` → приоритетный план | Анализ исходников не равен проверке в браузере |
| Презентационная страница вне рабочего приложения | Taste → Impeccable → реализация → приёмка | Не переносить язык рекламной страницы в рабочие разделы |

Impeccable отвечает за структуру, иерархию, типографику, компоновку, согласованность, доступность и окончательную доводку. Taste помогает выбрать и ограничить визуальное направление. Emil помогает объяснять изменения состояния движением после того, как статический сценарий работает.

Внешние наборы не считаются установленными от одного упоминания в инструкции. Перед использованием проверить реально доступный локальный `SKILL.md`, название операции, версию/commit и условия использования. Не вызывать вымышленные команды `init`, `layout`, `animate` и подобные по памяти. При отсутствии внешнего набора использовать действующую локальную роль и явно отметить это в передаче задачи. Не устанавливать пакеты и не загружать сторонний код автоматически, особенно на целевой машине. Внешние навыки — инструменты разработки, не зависимости приложения.

## 4. Исследование перед изменением

Прочитать `AGENTS.md`, `docs/design.md`, `docs/UX_FLOWS.md`, `docs/ADAPTIVE_UX.md`, профильные документы и соответствующие тесты. Зафиксировать точный commit. Проверить `public/index.html`, серверную вставку модулей в `apps/api/src/http-utils.mjs`, прямые и динамические импорты, шаблонные строки, программное создание DOM и делегированные обработчики.

Для каждого рабочего объекта определить пользователя и роль, вход, цель, необходимые сведения, главное действие, вторичные действия, источник истины, результат, возможные ошибки и возврат. Найти существующий компонент и сценарий до создания нового. Не менять Node/vanilla JS/CSS на другой стек ради оформления.

Выбрать глубину: L0 — ошибка/доступность; L1 — согласованность и доводка; L2 — компоновка/компонент; L3 — изменение сценария. Переход на следующий уровень требует объяснимой пользовательской причины.

## 5. Полнота: каждый экран, окно и элемент

При полном аудите использовать `docs/design/full-interface/PLAN.md` и реестр, создаваемый `tools/ui-audit/`. Единица учёта — конкретное место создания элемента в конкретном исходнике, а не название раздела. Отдельно учитывать настольную и мобильную кнопки, один контейнер окна с несколькими формами, системные `alert`/`confirm`/`prompt`, поля, варианты выбора, меню, раскрытия, ссылки, нестандартные интерактивные узлы и обработчики.

У каждой записи должны быть: постоянная ссылка на исходный commit, путь/строка/столбец, тип и подпись либо выражение, сценарий/контекст, исполнитель, решение `сохранить / исправить / объединить / удалить после доказательства недостижимости`, план действия, критерий приёмки, проверяемые состояния и статус. Одинаковый компонент не позволяет исключить остальные места его использования.

Повторяющаяся строка таблицы — один шаблон плюс обязательные варианты данных, а не бесконечное число записей. Динамические варианты, неподключённый код и неизвестные связи обработчиков не пропускать: заводить отдельную запись на уточнение. Не считать кандидата доказанно кликабельным или файл доказанно мёртвым только по статическому сканированию.

Любая новая/удалённая/перенесённая кнопка или форма требует сверки реестра. Полный аудит нельзя закрыть, пока остаётся элемент без исполнителя, сценарий без результата, окно без проверки закрытия или необъяснённая динамическая ветвь. Наличие записи в плане не означает, что исправление выполнено.

## 6. Рабочий интерфейс и визуальная система

Источник истины — существующий `docs/design.md`; не создавать конкурирующий `DESIGN.md`. Сначала задача → информация → структура → взаимодействие → визуальная система → движение → доводка.

Переиспользовать компоненты, переменные, типографику и пространственную систему. Предпочитать минимальное исправление токена/компонента отдельной переписи страницы. Данные сравниваются в таблицах, а не превращаются в декоративные карточки. Для чисел полезны табличные цифры; единицы и даты должны быть ясны. График обязан отвечать на конкретный вопрос с подписанными осями, единицами и периодом.

Не добавлять карточки внутри карточек, случайные градиенты, стекло/blur, неон, сияние, огромные радиусы, лишние тени, бессмысленные плашки, одинаковые рекламные блоки, emoji вместо единой системы значков, пустые слоганы и выдуманные показатели. Цвет сообщает состояние, но не является единственным носителем смысла. Текст — русский, короткий и предметный; существенное действие не прятать за непонятным значком.

Taste может предложить ограниченные варианты только при доказанной визуальной проблеме. Выбрать одно направление, записать решение в действующую дизайн-систему и прекратить переизобретение. Рабочая система требует низкой декоративности, достаточной плотности и минимальной анимации.

## 7. Формы, состояния и безопасность действий

У поля есть видимая подпись, подходящий тип, понятный формат/диапазон и ошибка рядом с причиной. Placeholder не заменяет подпись. Не запрашивать сведения, уже однозначно известные из выбранного объекта. Дополнительные поля раскрывать последовательно, но не прятать ошибки и блокирующие условия.

Для каждого применимого элемента проверить обычное состояние, наведение, фокус, нажатие, выбор, недоступность с причиной, загрузку, пустые данные, ошибку, частичный успех и успешное завершение. Для асинхронной операции добавить повторный клик, отмену/уход, устаревший ответ, недоступность сервиса и повтор запроса. Ошибка сохраняет ввод; успех означает подтверждённый результат сервера.

Для окна проверить все его варианты: открытие, заголовок, первоначальный фокус, Tab/Shift+Tab, Escape, крестик, «Отмена», нажатие вне окна, возврат фокуса, несохранённые изменения, прокрутку, повторное открытие и вложенное окно. Неприменимое состояние отмечается с причиной, а не молча пропускается.

Удаление, права и необратимые последствия требуют ясного предметного подтверждения. Обратимые рутинные операции не обрастать лишними подтверждениями. Архив источника не удаляет рабочий объект. Ручная правка не уничтожает извлечённое значение и locator. Поиск, календарь и отчёты остаются проекциями; ЛЛМ не утверждает факты и не блокирует базовый сценарий.

## 8. Доступность, адаптивность и движение

Проверять семантический HTML, доступное имя, клавиатуру, видимый фокус, контраст и активную область; не заменять всё наборами div. Полный аудит включает мобильный, планшетный, ноутбучный и широкий экран, длинные русские подписи, масштабирование и виртуальную клавиатуру. Плотную таблицу адаптировать без потери действий, единиц и связей.

Анимация объясняет появление, исчезновение, перемещение или причинную связь. Она быстрая, прерываемая и не задерживает действие. Обычно достаточно короткого перехода порядка 120–250 мс, но это ориентир, а не обязательная длительность. Предпочитать `transform`/`opacity`; не добавлять библиотеку ради одного перехода. Не делать непрерывных фоновых эффектов.

`kafedra-motion` подключается при реальном изменении переходов/жестов/движения. Решение `no-motion` полноценное. `prefers-reduced-motion` сохраняет понятное статическое состояние. Не анимировать изменения прав, подтверждений или важных значений так, чтобы скрывался смысл. Приоритет реализации: существующий CSS → браузерные возможности → действующая библиотека → новая зависимость только с доказанной необходимостью.

## 9. Передача работ и проверка

Порядок существенной работы: исследование → аудит → определение сценария → проектирование → реализация → движение только при необходимости → проверка → доводка. Роли и границы записаны в `codex/agents/design-team.md`. Один общий контракт/файл меняет один владелец; параллельные задания ограничиваются отдельными предметными областями.

Проектировщик передаёт не абстрактное пожелание, а идентификаторы элементов/сценариев, текущее и целевое поведение, ограничения, конкретные проверки и зависимости. Исполнитель не закрывает свою работу независимым `PASS`. Аудитор отдельно отличает доказательство исходниками, существующий тест, выполненный тест, браузерную проверку и проверку на целевой Astra Linux.

Полнота исходного реестра, полнота запланированных проверок и фактически выполненная приёмка — три разные величины. Не писать «проверено всё» по количеству найденных тегов или по одному снимку. Не выдумывать измерения, отзывы, скорость и статистику. Демонстрационные данные обозначать явно; реальные документы для целевой приёмки не заменять синтетическими.

## 10. Условие завершения

Главное действие очевидно, сценарий заканчивается устойчивым результатом, состояние и происхождение понятны, ошибки исправимы, интерфейс работает без цвета/анимации/ЛЛМ там, где они необязательны. У затронутых записей есть проверяемое решение и доказательство. Не выполнять бесконечный редизайн уже понятного и согласованного элемента.

В итоговом сообщении сообщить: что действительно изменено, где находится полный план/реестр, что проверено, что осталось непроверенным. Не выдавать план за реализованный интерфейс, наличие внешнего навыка — за его запуск, а назначенную роль — за завершённую работу отдельного агента.
